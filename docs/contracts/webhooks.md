# Merchant webhooks

Part of foundation document 3 (`README.md` §8). Wave 4. Governed by ADR-0024 (outbox), the proposed ADR-0027 (envelope) and the proposed ADR-0030 (signing and delivery). The catalogue is exactly the rows of the domain model §6.3 marked "Webhook: yes"; nothing here adds an event. Machine-readable twin: the `webhooks:` section and the `Wh*` payload schemas of `openapi/public.yaml`.

## 1. Envelope

Every delivery is one event in the ADR-0027 envelope (document 2 §6.1, `Envelope` in `components.yaml`): `id`, `type`, `version`, `occurred_at`, `account_id`, `aggregate_type`, `aggregate_id`, `sequence`, `causation_id`, `correlation_id`, `payload`. All catalogue events are `version` 1. Money is `{ "amount": <halalas>, "currency": "SAR" }`; times are ISO 8601 with offset.

```json
{"id":"0192f3a1-7c4e-7b11-9a2b-6f0d1c2e3a4b","type":"delivery.order.delivered","version":1,
 "occurred_at":"2026-10-31T14:05:12+03:00","account_id":"0192e000-0000-7000-8000-000000000001",
 "aggregate_type":"order","aggregate_id":"0192f100-1111-7222-8333-444455556666","sequence":9,
 "causation_id":"0192f3a1-7c40-7000-8000-00000000abcd","correlation_id":"0192f0ff-0000-7000-8000-00000000c0de",
 "payload":{"order":{"id":"0192f100-1111-7222-8333-444455556666","number":"D-000123","kind":"delivery","status":"delivered","source_ref":"SALLA-99812","site_id":"0192e000-0000-7000-8000-0000000000aa","cod_amount":{"amount":15000,"currency":"SAR"},"version":9},
  "delivered_at":"2026-10-31T14:04:58+03:00","point":{"lat":24.7136,"lng":46.6753},"proof_ids":["0192f3a0-0000-7000-8000-0000000000p1"],
  "cod":{"amount":{"amount":15000,"currency":"SAR"},"collections":[{"method":"cash","amount":{"amount":15000,"currency":"SAR"}}]}}}
```

## 2. Signing (ADR-0030)

| Header | Value |
|---|---|
| `X-Eeasy-Timestamp` | Unix seconds when this attempt was signed |
| `X-Eeasy-Signature` | `v1=<hex HMAC-SHA256(secret, "<timestamp>.<raw body>")>`; during a secret rotation two values, comma separated |
| `X-Eeasy-Event-Id`, `X-Eeasy-Event-Type`, `X-Eeasy-Delivery-Id` | copies of `id`, `type` and the delivery id, for logging only; never trusted without the signature |

Receiver rules: compute the HMAC over the raw bytes before parsing JSON; compare in constant time; reject a timestamp more than 300 seconds (5 minutes) from now; deduplicate on the envelope `id`. The timestamp is inside the signed string, so a captured request cannot be replayed with a fresh timestamp. The secret is generated by us (32 random bytes), shown once in the create or rotate response and stored encrypted; `rotate-secret` issues a new one and both sign for 24 hours.

## 3. Delivery

- **At least once.** A 2xx response within 10 seconds acknowledges. Anything else, a timeout or a connection error is retried. Receivers must be idempotent on `id`.
- **Ordered per aggregate.** For one subscription, at most one delivery per `aggregate_id` is in flight, in `sequence` order (document 2 §6.2). A retrying event holds back later events of the same aggregate only; other aggregates keep flowing (K-11). Receivers still compare `sequence` with the last one they stored and ignore lower values.
- **Retries.** Exponential backoff with jitter: 30 s, 2 min, 10 min, 30 min, 1 h, 2 h, 4 h, then every 4 h until 24 h after the first attempt. Then the delivery is `dead`, the aggregate queue moves on, and the gap is visible to the receiver as a jump in `sequence`.
- **Dead letters.** Dead deliveries are listed in the merchant web app (`GET /v1/staff/webhook-subscriptions/{id}/deliveries?status=dead`) and through the public API, with the last status code and error, and can be redelivered one by one. Platform staff see them as outbox rows of kind `webhook` (ADR-0024).
- **Suspension.** A suspended account's deliveries pause and resume on reactivation (K-2). A subscription whose deliveries have all been dead for 72 hours is set to `disabled` and the account owner is notified.
- **Effects come from the outbox.** A webhook is an outbox row written in the business transaction (ADR-0024, K-10); no request handler calls a merchant URL.

## 4. Subscriptions

Operations are in `public.yaml` (API key with `core.webhooks.manage`) and, identically, in `staff.yaml` for the web app:

| Operation | Path (under `/v1/public` or `/v1/staff`) |
|---|---|
| list, create | `GET`, `POST /webhook-subscriptions` |
| get, update, delete | `GET`, `PATCH`, `DELETE /webhook-subscriptions/{subscription_id}` |
| verify | `POST /webhook-subscriptions/{subscription_id}/verify` |
| rotate secret | `POST /webhook-subscriptions/{subscription_id}/rotate-secret` |
| send a test | `POST /webhook-subscriptions/{subscription_id}/test-deliveries` |
| delivery log, redeliver | `GET /webhook-subscriptions/{subscription_id}/deliveries`, `POST …/deliveries/{delivery_id}/redeliver` |
| catalogue with samples | `GET /webhook-event-types` |

**Scope (H3).** A subscription stores `created_by_key_id` (public API) or `created_by_membership_id` (web app). Each event type needs the creator's matching read permission, checked at create, at update and before every delivery:

| Event types | Required permission |
|---|---|
| `delivery.order.*`, `delivery.cod.*` | `delivery.orders.read` |
| `delivery.proof.*` | `delivery.proofs.read` |
| `wms.stock.*` | `wms.stock.read` |
| `wms.fulfilment_order.*`, `wms.package.*` | `wms.fulfilment.read` |
| `wms.inbound_receipt.*`, `wms.return.*` | `wms.receipts.read` |

A missing scope at create or update returns `403 forbidden` with `details.missing_scope`. When the creating key is revoked or loses a scope, or the creating member is revoked, the subscription becomes `paused` with `paused_reason` and nothing more is sent until a principal with the scope resumes it; resuming rebinds `created_by_*` to that principal (N12).

**One-time verification token.** Creating a subscription (or changing its URL) sets `status = pending_verification` and sends one signed `webhook.verification` request to the URL whose body carries a single-use `verification_token`, valid 24 hours and stored only as a SHA-256 hash. The integrator calls `verify` with that token; only then does the subscription become `active` and receive events. This proves control of the URL without asking the receiver to echo anything synchronously. URL rules (ADR-0030): `https` on port 443 only; at create the API checks syntax and address class only (`webhook_url_invalid`); the reachability check and the verification request are outbox effects. At every delivery the worker resolves the name once, refuses private, loopback, link-local, `0.0.0.0/8`, `100.64.0.0/10`, `198.18.0.0/15`, multicast and IPv4-mapped IPv6 addresses, connects to the checked IP with the original host name for TLS, and follows no redirects. The delivery log shows the HTTP status and a fixed `error_class` (`timeout`, `dns_error`, `connection_refused`, `tls_error`, `address_refused`, `redirect_refused`, `http_status`), never the receiver's response body. Subscription create and URL change are limited to 5 per hour per account.

**Test and samples (Bolesa pattern, foundation plan §9).** `GET /webhook-event-types` returns every event type with its version, Arabic and English description and a sample envelope; the web app renders it as the samples page. `test-deliveries` signs and sends the sample of a chosen type to the subscription now, marked `"test": true` in the delivery log and `X-Eeasy-Delivery-Id`; tests ignore event-type filters and never enter the ordering queue.

## 5. Catalogue

All events are version 1. Ordering scope is the aggregate in the event name (document 2 §6.3).

| Event | Trigger (document 2 state machine) |
|---|---|
| `delivery.order.created` | an order is created by any intake (§3.1) |
| `delivery.order.accepted` | pending → accepted, or an order taken back to accepted (§3.13) |
| `delivery.order.assigned` | offer accepted or direct assignment |
| `delivery.order.picked_up` | assigned → picked_up |
| `delivery.order.out_for_delivery` | picked_up → out_for_delivery |
| `delivery.order.attempted` | out_for_delivery → attempted (D-14) |
| `delivery.order.delivered` | out_for_delivery → delivered (D-7) |
| `delivery.order.failed` | out_for_delivery or attempted → failed |
| `delivery.order.returned` | failed → returned at the site |
| `delivery.order.cancelled` | a pre-pickup state → cancelled |
| `delivery.order.rescheduled` | a new slot is booked by a dispatcher or the recipient |
| `delivery.proof.stored` | a proof file reaches `stored` (§3.10, D-17) |
| `delivery.cod.collected` | a COD collection is recorded (§3.11, D-18) |
| `wms.inbound_receipt.received` | receiving → received (§4.11) |
| `wms.stock.available_changed` | a product's available quantity changes (§4.5) |
| `wms.fulfilment_order.created` | a fulfilment order is received (§4.12) |
| `wms.fulfilment_order.on_hold` | received or picking → on_hold |
| `wms.package.packed` | open → packed (§4.14) |
| `wms.package.shipment_created` | awaiting_label → ready with AWB and label |
| `wms.package.handed_over` | ready → handed_over |
| `wms.fulfilment_order.completed` | handed_over → completed |
| `wms.return.received` | a return is received (§4.8, W-17) |

### 5.1 Payloads

`order` is the common block of every `delivery.order.*` payload: `id` (uuid), `number` (string), `kind`, `status`, `source_ref` (string or null), `site_id` (uuid), `cod_amount` (Money), `version` (integer, equals `sequence`). `driver` is `{ id, first_name }`; no driver phone or surname leaves the system.

| Event | Field | Type | Note |
|---|---|---|---|
| `delivery.order.created` | `order`, `source`, `recipient`, `address` | block, enum, Recipient, Address | `source ∈ {manual, csv, api, channel, wms_package}` |
| `delivery.order.accepted` | `order`, `zone_id`, `slot` | block, uuid, `{starts_at, ends_at}` or null | |
| `delivery.order.assigned` | `order`, `driver`, `vehicle_kind` | block, driver, enum | `car`, `van`, `motorbike` |
| `delivery.order.picked_up` | `order`, `driver`, `picked_up_at` | block, driver, date-time | |
| `delivery.order.out_for_delivery` | `order`, `eta`, `tracking_url` | block, date-time or null, uri | recipient link, purpose `track` |
| `delivery.order.attempted` | `order`, `attempt_number`, `reason_code`, `attempted_at` | block, integer, string, date-time | reason from the account list |
| `delivery.order.delivered` | `order`, `delivered_at`, `point`, `proof_ids`, `cod` | block, date-time, Point, uuid[], `{amount, collections[{method, amount}]}` | proof files via `GET /orders/{id}/proofs/{proof_id}/download-url` |
| `delivery.order.failed` | `order`, `reason_code` | block, string | |
| `delivery.order.returned` | `order`, `returned_at`, `items` | block, date-time, `[{sku, quantity}]` | |
| `delivery.order.cancelled` | `order`, `reason_code`, `actor_type` | block, string, enum | `user`, `api_key`, `system` |

| `delivery.cod.collected` | `order_id`, `order_number`, `collection_id`, `amount`, `method`, `custody` | uuid, string, uuid, Money, enum, enum | custody `collected` (cash) or `not_held` |

| `wms.package.shipment_created` | `package_id`, `fulfilment_order_id`, `carrier_code`, `awb`, `label_url` | uuid, uuid, string, string, uri | label URL expires |
