## 0. Goal

A dispatcher creates an order of any kind for a site with a recipient, an address and items, and the API numbers it gap-free per account, geocodes the address through the short code or the text, resolves the zone through the site's coverage, applies the account's intake rule (accept at once, or receive as pending) and leaves an uncovered or unlocated order `pending` with a typed reason; the dispatcher lists, reads and edits orders with optimistic concurrency, accepts, fails and cancels them along the state machine's dispatcher arrows with an append-only event per change, so that DEL-6 can offer and assign, DEL-7 can replay the driver's events against the same machine, and WEB-5 can render orders from one contract.

## 5. Exit criteria

- An order of each kind is created with a gap-free number, a geocoded point, a zone and the intake rule's status; an uncovered or unlocated order is `pending` with its reason and cannot be accepted.
- Twenty parallel creates number consecutively; a rolled-back create leaves no gap.
- Every dispatcher arrow of §3.13 works with `If-Match` and refuses a stale version or an illegal arrow with the documented `409`; a terminal order never changes.
- `del_order_events` refuses updates and deletes; a replayed create or transition returns the original result.
- No audit row, outbox payload or log line carries a recipient's name or phone; both RLS lanes green; no contract change.

### 8.2 Notes

1. **`core_sequences` (2.1, 2.2).** No migration on `main` created it, so this one does, as data §2.1 names it (`next_value`, the name CHECK of §7), not the plan's `value`. Provisioning does not create the rows yet, so `SequenceAllocator` upserts (`INSERT … ON CONFLICT DO UPDATE`, the row lock held to commit) through a new `ScopedRepository.upsert` in `packages/db`, whose target must lead with `account_id`.
2. **Columns beyond data §2.2 (2.1).** `del_order_items.position` keeps the request's item order (UUIDv7 ids of one millisecond are not monotonic); `del_order_events.note` is the contract's `OrderEvent.note`; a CHECK ties `type = transition` to a `to_status`. `idempotency_key` is nullable (system events carry none). `elx_platform` reads the four tables and writes none.
3. **D-4 code (2.3).** The plan says `400 validation_failed` at `/body/cod_amount`; `createOrder` and errors.md name `422 cod_not_allowed` for exactly this, so the door answers that (`details.kind`, `details.cod_amount`). The lead may overrule; the change is one line in `order-input.ts`.
4. **`needs_location` on the contract (2a).** `Order.pending_reason` listed only `outside_coverage`, `awaiting_review`; the presenter could not return the third reason, so `components.yaml` gains the value (§8.1). README §2 counts a new value of a non-extensible enum as breaking; no client reads orders yet (WEB-5 not started).
5. **Geocode timing (2.4).** `@Idempotent()` needs the request's transaction, so the geocoder cannot run before it opens. It runs first in the handler, after the site check and before any lock or write; the transaction holds only the idempotency reservation during that I/O.
6. **Monthly order limit (2.3).** The plan is silent. The contract lists `422 limit_exceeded` and `core_usage_counters` says DEL-2 counts orders. Intake upserts the `orders` counter in the order's transaction and refuses past `limits.orders_per_month`; a refusal rolls the count and the number back. `OrderAccounts` (kernel) reads the settings and limits on the platform pool, as `AccountService` does.
7. **Item directions (2.3).** The generated schema fills `direction: out`, so a sent `out` and an omitted one look the same. `return_pickup` and `pickup_request` items are always `in`, `exchange` keeps what was sent, and an `in` item on a `delivery` order is `400` at its `direction`.
8. **Sites (2.3).** An unknown, foreign or inactive site is `400 validation_failed` at `/body/site_id` (DEL-4's home-site rule); a warehouse is `422 site_kind_mismatch`. `@SiteScoped({ from: 'body' })` is on the door, but no site-scoped bundle holds `delivery.orders.create`, so nothing tests it.
9. **Machine extras (2.6, 2.9).** `picked_up → failed` (dispatcher) is in the machine for Q-6's cancel after pickup; §3.13's diagram lacks it but its closing note implies it. A short-code hit stores the source's own confidence (1 from the register and the stub, 0.95 from Sayyar), not a fixed 1.0. The created event's `payload` carries `pending_reason`.

10. **Missing `If-Match` (2.8).** The plan says `400` at `/header/if-match`; the `IfMatch` parameter, errors.md and README §5 say `428 version_required`, so the contract pipe answers that for every operation that declares the header (DEL-6's doors too). A malformed value (`W/"1"`, `*`, a list) is the plan's `400`. `getOrder` sends `ETag: "<version>"`.
11. **What locks (2.8).** `cod_amount` locks from `picked_up` with recipient, address and items (the `updateOrder` description; custody follows the amount); notes stay editable until terminal. `order_locked` names the refused parts in `details.locked` (the Error schema reserves `details.fields` for field problems).
12. **Address edits (2.8, integrations §6.2).** A text-only edit keeps a `recipient_pin`, `driver_pin` or `manual` point (higher trust than the geocoder) and only re-resolves the zone. An `accepted` or later order whose new point no zone covers keeps its status with `zone_id` null: DEL-6 refuses the offer (`outside_coverage`). A pending order made acceptable under `auto_accept` takes a system arrow, so the answer is `version + 2`.
13. **Site use (lead ruling).** `open_orders` counts every non-terminal status (`failed` too: the parcel comes back). To close the create/deactivate race, intake holds the `core_sites` advisory lock shared (new `ScopedRepository.sharedTransactionLock`, kernel `holdSites`) after the geocoder and re-checks the site under it.
14. **List (2.7).** Sorts `created_at` (default), `updated_at`, `number` (zero-padded text keyset) and `status`, as the contract lists; `zone_id` filters too (contract). `q` matches the name, a phone tail of at least four digits, or the number; a bad `number` is `400`. Keyset values are the timestamps' text (microseconds kept). Events sort `server_ts` ascending by default.
15. **Events (2.8).** `server_ts` is `clock_timestamp()`, so an edit's note and the arrow it causes keep their order. The note event's `payload` (changed parts) is not on the `OrderEvent` contract, so the API timeline shows a `note` with no text; WEB-5 may want a contract field. Row locks: `ScopedRepository.findMany` gained `forUpdate`.
16. **Outbox types (2.9).** The plan names one `delivery.order.status_changed`; catalogue §6.3, the stream and the webhook list name one type per status, so `OrderTransitions.apply` writes `delivery.order.<to_status>` (payload: order, number, from, to, reason code, actor type, site, zone; no recipient data). Ten types appended to `domainEventTypes`; F adds the catalogue note.
17. **Cancel after pickup (2.9, Q-6).** As the plan says, `cancelOrder` on `picked_up`, `out_for_delivery` or `attempted` lands `failed` with the reason; the operation's description still says "before pickup … after pickup use fail". The contract text is the lead's to align (no shape change).
18. **Reason codes (2.9).** `failed` and every cancel need one of the account's codes; `active: false` codes are no longer offered (`orderAccountOf`). A new account has no codes (PLAT-12 default `[]`), so it cannot cancel until an owner adds some: provisioning or WEB-5 should seed defaults.
19. **One write path (2.10).** `OrderTransitions.apply` (row `FOR UPDATE`, `If-Match` when sent, the machine, D-3 on `accepted`, event, audit `delivery.order.transitioned` when request facts are passed, outbox) and `OrderReader.byId` are Delivery public; DEL-6 and DEL-7 pass their own actor. A `reason_code` on `accepted` is optional but checked when sent.
