## 0. Goal

A dispatcher plans a shift for a driver at a site with a vehicle, and the driver starts it from the app (or starts an ad hoc one), pauses, resumes and ends it through replayable doors; the API ends shifts a dispatcher cancels, marks planned shifts the driver never started as no-shows after a grace period, and ends every active shift of an account that gets suspended; while a shift is active or paused the app posts position batches that land in a bounded per-driver ring, the newest point in Redis for maps, and on a per-account channel for the streams DEL-6 builds; a worker appends the ring to a simplified daily trail kept 90 days and raises a stale-tracking alert to the driver and dispatch when an active shift sends nothing for 5 minutes; staff read the latest positions per site and a driver's trail for a day, so that DEL-6 can offer only to drivers on shift and the dispatch board can show where they are.

### 2a. Lead's improvements over the roadmap row

- **Eligibility reasons are typed** (`details.reason`, 2.4) so DRV-3's shift screen can say why instead of showing a generic refusal.
- **The replay marker gets its first use** (2.4): pause, resume and end answer the app's outbox replays by key, which DEL-7's order events will copy.
- **An ad hoc shift has a bounded window** (12 hours) and planned shifts a start window, so a forgotten shift cannot stay live for days and the sweeper has a rule to close on.
- **The stale alert is rate-limited and recorded on the shift** (2.8), so a driver in a tunnel gets one push every 15 minutes, not one every sweep.
- **Ingest never depends on Redis** (2.6): the head row is the fallback the maps read when Redis is down, as data §6 asks.
- **The suspension consumer** closes PLAT-13's open thread (8.2 #35) in the order that owns shifts.

## 5. Exit criteria

- A driver starts a planned or ad hoc shift only when eligible, with the reason otherwise; pause, resume and end replay by key; a dispatcher can plan, cancel and end; a no-show is marked at the grace; suspension ends the account's shifts.
- 250 points leave 240 in the ring with the newest in Redis and on the channel; the ingest answers `202` without Redis; the budget holds.
- The trail of a day is one simplified line that grows only with new points and survives a second run unchanged; trails older than 90 days are deleted.
- An active shift silent for 5 minutes alerts the driver once per 15 minutes and raises the event once.
- No log line or event payload carries a position; both RLS lanes green; `DriverLocationPoint` regenerated with the two fields.

### 8.2 Notes

1. **Grants (2.1).** All four tables: elx_app CRUD, elx_platform SELECT only (the plan names shifts; I applied the same to the ring, heads and trails). Leg 2's jobs therefore scan on the platform pool and write per account in elx_app transactions (the worker's app pool, as the internal-event consumers do); a job that must write cross-tenant needs a grant in its own migration.
2. **Keys without `account_id`.** `globalUniqueIndexes` gains `del_driver_shifts (driver_id)` (the live partial index), `del_driver_locations (driver_id, slot)` and `del_driver_location_heads (driver_id)`: a driver id belongs to one account. `pii:driver` on `point`, `last_point`, `path`. The shift table adds `stale_alerted_at` (2.8) and CHECKs `started_at` set once started, `ended_at` set iff `ended`.
3. **Refusal codes (2.3, 2.4).** A body id not of the account is `400` at its pointer (`invalid`, DEL-1 8.2 #4); an inactive site `409 invalid_transition`; a non-`active` driver or an inactive vehicle on `planShift` `422 driver_not_eligible` with the reason; an overlap `409` with `shift_id`, `current_status`, `version` and the window. On the driver doors `driver_suspended` is shadowed by `tokenDriver()`'s `401 token_invalid` (DEL-4 M-2 runs first); the reason stays in the typed list and its unit test.
4. **Audit and events (2.9).** Driver starts and ends are audited with `actor_type driver`, `actor_id` = the driver row id (DEL-4's driver doors used `user` + person id); pause and resume write no audit row and no event (2.9 names neither). `delivery.shift.started` carries `shift_id`, `driver_id`, `site_id`, `vehicle_id`, `started_at`, `ad_hoc`; `.ended` `ended_at`, `ended_by`, optional `reason`; aggregate `driver_shift`.
5. **Budget (2.6).** A named budget `driver_locations` (12 a minute, key `driver:<id>`) is charged after the live-shift check, so a `409` costs nothing; README §7's route budget (12 a minute per device) stays in the global guard. Both fail open without Redis.
6. **Points (2.6).** A coordinate, accuracy or battery out of range (or a non-finite speed or heading) makes the whole batch `400` at the point's pointer; a future (> 5 min), too old (> 24 h) or not-newer point is dropped and counted in `driver_pings_total{outcome}`. The ingest is `@NoUnitOfWork()` under the driver row lock, so batches of one driver and a shift end serialise; Redis is written after commit with the API clock as `server_ts` (the ring's `server_ts` is the database's `now()`).
7. **Latest read (2.7).** The plan's "MGET" reads hashes, so it is one pipeline of `HGETALL`; the shift status comes from the live shift row, not the hash. Drivers on shift without any point are left out. Ending a shift (driver or dispatcher) deletes the latest key in the door, before the commit (Redis is never the truth).
8. **Trail (2.7).** `404` for a driver not of the account and for a day without a row; `business_date` defaults to today in Asia/Riyadh; `line` is `ST_AsGeoJSON(ST_Force2D(path))`. Only the latest door is `@SiteScoped()` (query `site_id`, plus `siteFilter`); no role holding `delivery.locations.read` is site-scoped (roles.yaml), so 2.10's site-scoped member case has no member to test with and is not written.
9. **Metrics.** `driver_pings_total{outcome}`, `driver_ping_lag_ms`, and the observed gauge `active_shifts{status}`, declared here and set by leg 2's sweeper. No log line or event carries a position; the fan-out's warning names only the operation and the error class.
10. **Contract (A-18).** `is_charging`, `power_saver` optional booleans on `DriverLocationPoint`, stored on the ring row; `generated/` is gitignored, so "identical twice" is a hash of all 875 generated files after two builds.
11. **Job writes (lead ruling on #1).** Each job lists accounts or drivers on the platform pool and writes on elx_app: one transaction per driver (appender), per account (sweeper, retention); a failure skips that driver or account with one warning. Locks follow `push-receipts.ts` (`SET NX PX`, 4 min, never released; retention 23 h), not data §6's "30 s, renewed". Runs take an `accounts` scope, used only by the integration suite (shared database).
12. **Trail (2.8).** Tolerance 0.000045° on the 4326 plane (5 m of latitude, ≤ 5.5 m of longitude in Saudi Arabia; no projection); M = `client_ts`; `point_count` counts ring points taken, not vertices; a one-point segment of a new day is that point twice (a valid line). Points the ring overwrote between runs are lost (5-minute runs against a one-hour ring).
13. **Retention (2.8).** A 15-minute tick runs it inside the 03:00 Riyadh hour; deletes `business_date < Riyadh today − 90 days`; no audit row (counts in the log).
14. **Stale (2.8, §7 #3).** "No point for 5 minutes" is the head's `last_server_ts` (arrival time), from `started_at` when no point arrived since; one alert per ≥ 15 minutes via `stale_alerted_at`, which bumps `version` so the event sequence keeps rising. Event payload: `shift_id`, `driver_id`, `site_id`, `last_point_at`, `alerted_at`.
15. **Push (2.8).** `stale_tracking`: channel `run`, high, sound; `data.kind` `sync`, route `eeasydriver://sync` (driver-app §8.2 has no tracking link; DRV-3 may add one); TTL 900 s, `collapse_id` `stale:<shift>`; locale from `core_users` read on the platform pool, `ar` if none; outbox type `delivery.shift.tracking_stale` on both rows. No-shows audit `delivery.shift.no_show` with actor `system` and the run id as request id. The sweep also sets the `active_shifts{status}` gauge.
16. **Suspension consumer (2.5).** One transaction per account, not per shift (the dispatcher's tenant unit of work holds the receipt; the lead's leg 1 ruling allows per account): drivers locked in id order, so the sweeper and the consumer never wait in a cycle. It ends shifts without deleting the Redis latest key (no Redis in the dispatcher); `listLatestDriverPositions` shows live shifts only, and the key expires in 600 s.
17. **Consumer listing.** `platformListConsumers` builds its registry from `kernelConsumers()`; the kernel may not import Delivery (architecture rule), so `delivery.account_suspended_shifts` runs but is not listed there. A port the app module fills would close it; left for the lead.
18. **Scenarios.** The plan's "twelve operations" are thirteen (six driver, seven staff); each has an unauthenticated `401` scenario like DEL-4's (no seeded session in the contract run). Not run against a live API locally (CI's contract lane).
19. **Docs.** domain model §6.3 replaces the `delivery.shift.started` / `.ended` row (consumer "telemetry gate") with three rows naming DEL-6's board and offers; data.md gains `stale_alerted_at` in the §2.2 row, the three DEL-5 locks with their real TTLs, and one paragraph on the jobs.
20. **F1 shifts close (round 1).** The sweeper ends `active`/`paused` shifts at `planned_end + 60 min` (no-shows, then these ends, then stale alerts, so an ended shift is never alerted); `updateDriver` leaving `active` ends the live shift in its transaction with `ended_by: system`, reason `driver_suspended`/`driver_archived`, audit actor `system` with the request's id (beside the member's `delivery.driver.updated`). The latest key goes through a new `afterCommit` hook in `packages/db` (`withUnitOfWork` only; a failing hook is ignored), now also in the sweeper and the consumer (`redisLatestForget` on the worker's client).
21. **F2 gate (round 1).** `@Feature('delivery')` on `DriverShiftsController` and `DriverLocationsController`. DEL-4's driver-auth doors (sign-in, refresh, `driverGetMe`, devices) stay ungated on purpose: a driver must sign in to learn the module is off, and the test shows `driverGetMe` answering `200` while the shift and location doors answer `403`.
22. **F3 Redis order (round 1).** The latest hash is written by a Lua script (`defineCommand` `elxLatestIfNewer`) that compares `client_ts` as ISO-8601 UTC strings (same length, so string order is time order) and writes only a strictly newer one, then the TTL; a kept-out write leaves the old TTL. The publish carries the head row `advance` returns (point, `last_client_ts`, database `last_server_ts`). Every latest-key delete is an `afterCommit` hook (8.2 #20); 8.2 #7's "before the commit" is superseded.
