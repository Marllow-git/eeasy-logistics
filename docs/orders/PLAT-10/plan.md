- **Status:** planned; brief after PLAT-8 closes (both touch `apps/api`, `packages/contracts`, `packages/db`)

## 0. Goal

Every operation on the staff, platform and driver surfaces is allowed only to a principal whose roles hold the operation's `x-permission`, site-scoped roles see and touch only their sites, and the role combinations the ledgers forbid cannot be created, so that PLAT-11 onward issue tokens into a frame where authorization is enforced by the kernel from the contracts, not by each handler.

## 1. Binding rules and ADRs

- AGENTS.md hard rules: tenancy from the token; ledgers (separation of duties, M9); config through `packages/config`.
- ADR-0025 "Decision"; ADR-0006 "Decision" (allowlist rollout; the `feature_not_enabled` check is PLAT-13's, this order leaves the hook).
- `docs/architecture/identity-and-tenancy.md` §2 "Roles and permissions" (flat permission strings; system roles in wave 0; the role table; site restriction is data on the membership; separation of duties: cashier never driver, no single role approves and records an adjustment above the threshold), §4 "Tokens and sessions" (claims `roles`, `sites`, `scopes`), §9 "Adversary checklist" items 1, 2 and 5.

## 5. Exit criteria

- Every non-public operation on the staff, platform and driver surfaces is refused without the required permission; the required permission comes only from the contracts.
- Site-scoped principals cannot see or touch another site's resources (404), and an empty site list sees nothing.
- The eleven bundles are seeded and equal README §11; the forbidden role combination cannot be built.
- The adversary pass finds no critical or high; identity §9 items 1, 2 and 5 answered in §9.

### 8.2 Interpretations the lead should check

1. **Doors are not bundle permissions.** `core.auth.anonymous`, `core.auth.self` and `platform.auth.self` appear in no bundle; the guard opens them to any principal of the operation's surface (plan 2.5). README §11 lists `platform.auth.self` for platform support and "every core … / every platform permission" phrases would include them; the parity test drops the three doors from README's sets and the lint rule refuses a door in a bundle. Behaviour is the same either way.
2. **"Every core, delivery and wms permission" = the core, delivery (staff) and wms rows.** Driver and recipient-token permissions are not in owner or admin (an owner holding `delivery.driver.cash` beside `delivery.cash.*` would break M9 inside one bundle); viewer reads only those rows' `*.read`.
3. **Where the guard reads the permission.** Plan 2.2 asks for `operationPermissions` and `crossTenantOperations` per surface; both are generated and exported. The kernel may not import the contracts (A-17), so each generated `operationSchemas` entry also carries `operationId`, `surface`, `permission` and `crossTenant` and is `Object.freeze`d; the guard reads them from the entry the handler binds. A hand-built or spread copy is not frozen: refused at boot (`OperationRoutesCheck`) and by an ESLint rule in controllers. `crossTenantOperations` has no consumer in the API yet (a later check could require `@CrossTenant()` exactly on those operations).
4. **`surface` column on `core_roles`.** Beside plan 2.3's `scope` and `site_scoped`: a bundle counts only on its own surface, so `owner` on a driver token or `driver` on a staff token grants nothing.
5. **Platform role claim.** A platform token's `roles` claim carries the `core_platform_staff.role` value (`super_admin`, `admin`, `support`, data §2.1), read as bundle `platform_<role>`; the bundle key itself in a platform claim grants nothing. PLAT-11 issues platform tokens accordingly.
6. **Denial audit failure.** A failed `core.authorization.denied` write is logged and the request still answers `403`: the refusal is the safe outcome, and the throttle already leaves repeats unaudited. The row's `after` holds operation, permission, surface and the token's roles; `targetType` `operation`.
7. **Throttle scope.** One row per principal (kind, user, account) and operation per fixed minute, per API process; N instances write at most N rows a minute per pair. Redis was not used, so a Redis outage cannot open the log to flooding. After lead review round 1: one key set per minute, replaced whole at the window change (O(1)), never evicting a current key; past 10 000 keys in one minute new denials go unaudited for the rest of that minute, logged once.
8. **Site scoping edges.** A permission is site-restricted only when every bundle granting it is site-scoped (viewer + site staff reads every site). Restricted with an empty `sites` claim: `404` on every operation of that permission, lists included (fails closed rather than an empty list). `@SiteScoped()`: a path or body site must be present (missing body site `404`, not `400`), a query site may be absent and the list filters with `siteFilter`. The guard normalises the `sites` claim once (`normaliseSiteIds`: lowercase, UUIDs only, no repeats) and both the scope check and `siteFilter` use that list (review round 1); the claim schema already refuses a token with a non-lowercase UUID. `siteFilter` reads sites bound to the frozen tenant context in a kernel `WeakMap`, so `packages/db` is unchanged; a context without a binding (jobs, drivers, platform) is unrestricted.
9. **`assertRoleCombination(roles, bundles)`.** Takes the resolver's bundles (two parameters, not plan 2.7's one). Lead ruling, review round 1: M9 means a driver never holds a cash-handling permission, read as `delivery.cash.receive`, `delivery.cash.deposit`, `delivery.cash.close_report` and `delivery.liability.record` (`cashHandlingPermissions`); `delivery.cash.read` handles no cash. So owner, admin and cashier are refused beside `driver`; viewer and dispatcher are allowed. Unknown roles are left to PLAT-12's validation.
10. **Without the platform pool** (outside production only) there is no resolver and role-checked operations answer `500 internal_error`; doors still pass. A missing `core_roles` table fails the boot.
11. **Test harness.** Existing probe routes now bind real operations (`test/support/probe-operations.ts`), and the test signer's default platform role is `super_admin` (was `owner`, which grants nothing on platform). No assertion was changed or removed.
