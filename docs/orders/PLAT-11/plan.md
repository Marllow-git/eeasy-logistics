## 0. Goal

A merchant staff user accepts an invitation, signs in with email and password, passes a phone OTP second factor when their account requires one, picks an account when they have several, keeps a 15-minute access cookie alive through a rotating refresh cookie whose reuse revokes the family, resets a forgotten password by email, and signs out everywhere; a platform staff user does the same with mandatory TOTP and a 12-hour idle expiry; every door answers the same to an unknown and a disabled user, every secret is hashed or encrypted, every session event is audited, and the first super admin exists without anyone editing the database, so that PLAT-12, PLAT-13 and WEB-2 build on real sessions instead of the test signer.

## 5. Exit criteria

- Every operation of the staff and platform `auth` tags answers per its contract, with the contract's error codes and no other.
- A rotated refresh token presented again outside the grace revokes its family; inside the grace the same token comes back; a password reset ends every session.
- Unknown, disabled and known users get the same body and a password verify of the same cost at `login`.
- TOTP is mandatory for platform sessions and a code cannot be replayed; the first super admin is created only through the bootstrap command.

Leg 2 (items F to J):

29. **Checking a code in three steps** (`auth/second-factor.ts`): the challenge is locked, checked and charged one attempt in a committed transaction, then PLAT-9's `OtpService.verify` runs in its own, then the challenge is locked again and consumed. No request holds two platform connections (a lock held across `verify` would, and a full pool would then wait on itself). Charging before the check makes the five a hard cap under concurrency: the fifth try may be right, the sixth is refused even with the right code (tested with the OTP's own count reset). `requestSecondFactor` refuses a challenge past five as `token_invalid`.
30. **Locale of the code:** the user's stored locale, not `Accept-Language` (the code may be requested from another device than the one that set the language).
31. **`verifySecondFactor`** continues with the challenge's pinned memberships that still allow sign-in (re-read), so a membership revoked between the steps is gone from the selection; none left is `otp_invalid` (the codes the operation lists). A factor asked by `selectAccount` or `switchAccount` pins the one target, so verifying it starts that session; the switch's old family is not revoked by the verify (the browser's refresh cookie is replaced; it ends at its own expiry or the next password reset).
32. **Enrolment `challenge_id`** (`EnrolChallenge`, `EnrolConfirmRequest`): the enrolment's own row id (the id half of the enrolment token); the row holds the pending phone, and a second `enrol` replaces it, so a code sent to an earlier phone no longer confirms. `expires_at` is the code's expiry (5 minutes), capped by the token's. The phone is normalised with PLAT-9's `normalisePhone`; an unparseable one is `400 validation_failed` at `/body/phone`. Confirm counts five attempts on the enrolment row; on success it answers `204` and the user signs in again (staff.yaml), audited `core.auth.second_factor_enrolled` with `via` (`sign_in` or `link`) and no phone.
33. **Second-factor reset** (`SecondFactorResets.issueLink`, kernel public, for PLAT-12): the identity tables are platform-pool only, so the reset itself lives here: `second_factor_enabled = false` with the phone kept as the marker of a reset, `token_version + 1`, every refresh family revoked (`revoked`), earlier links spent, a 24 h `enrolment_link` challenge, a mail and the audit row `core.auth.second_factor_reset` (actor the manager PLAT-12 passes; PLAT-12 audits its own reason). With the marker, the password alone gets `enrolment_required` on an account that requires a factor but `enrol` answers `409 second_factor_already_enrolled` (staff.yaml: "after a reset the password alone cannot"); on an account that requires none the user signs in without a factor until they re-enrol. The old phone no longer receives sign-in codes.
34. **Emailed link:** a new mail template `second_factor_reset` (ar and en in `packages/i18n`, registry entry with `link` as its link parameter, domain event type `core.second_factor.reset`), link `PUBLIC_WEB_URL/second-factor/enrol/<id>.<secret>`: web.md §1 names no route for it, so WEB-2 adds the page (lead to note for WEB-2). The plan's paths said no new template; the contract's "emails a one-time re-enrolment link" and the lead's item J (enrolment-link tokens on outbox rows) need one.
35. **`redeemEnrolmentLink`** turns the link row itself into the enrolment token: a new secret (the link's stops working), `amr = ['pwd']`, 10 minutes; a wrong password is `401 invalid_credentials` and counts an attempt on the link (five end it, then `token_invalid`); an unredeemed link is no enrolment token. Budget `auth_token_ip` (20 an hour per address). `verifySecondFactor`, `confirmSecondFactor` and the TOTP doors have no budget of their own beyond the five attempts per challenge and the surface budget: a new challenge needs a password step, which is budgeted.
36. **TOTP** (`auth/totp.ts`): `node:crypto` HMAC-SHA-1, 30 s, six digits, ±1 step; every candidate step is compared with `timingSafeEqual` whatever matched; the accepted step is the oldest matching step in the ±1 window above `totp_last_step` (RFC 6238 §5.2; in practice one step matches a given code), written in the transaction that starts the session, so the confirming code and any earlier step are refused afterwards (the replay guard). The secret is stored as its base32 text encrypted with the credentials cipher: under `core_auth_challenges:<id>` while pending, re-encrypted under `core_platform_staff:<user_id>` with `totp_key_id` at confirm. A blob that does not decrypt (a retired key) counts as a wrong code. The pending ciphertext stays on the consumed challenge until the purge (7 days, item H); it decrypts only with the credentials key.
37. **TOTP door codes:** verify and confirm answer `otp_invalid` for an unknown, used or exhausted challenge, a wrong or replayed code, a disabled user or a revoked staff row, and count an attempt whenever a challenge was found; `token_expired` for an expired challenge. Enrol answers `token_invalid` (unknown, used, exhausted), `token_expired`, `reauthentication_required` when the challenge lacks `pwd` (every challenge this order mints has it; the code guards a later minting path), and `409 second_factor_already_enrolled`. A second enrol on the same challenge replaces the pending secret and answers a new URI. The URI uses `AUTH_TOTP_ISSUER` and the user's email; it is never logged nor audited (the audit row carries the key id only).
38. **`platformLogin`** refuses with one body and one password check users who are unknown, disabled, password-less, without a staff row or with a revoked one; a merchant member is not platform staff. Budgets `platform_login_email` and `platform_login_ip` (10 and 50 an hour, apart from the staff door's counters).
39. **`platformAcceptInvitation`** finds the user by the invitation's email (`createPlatform` found or created it), sets the password and name (a user who already had a password has every family revoked, as on the staff side), and grants the staff row: a new row with the invited role and `granted_by` = the inviter; a revoked row comes back with its TOTP cleared; a live row takes the role and keeps its TOTP. Audited `core.invitation.accepted` (account NULL, actor type `platform_user`). The answer is a `totp` challenge with `totp_enrolment_required` from the row.
40. **Platform sessions** carry `roles: [<staff role>]` and `amr: ['pwd', 'totp']`; `platformRefresh` and `platformLogout` are leg 1's `SessionService` paths (sliding 12 h, family revocation); the leg 1 test door stays in `sessions.http.test.ts` for the grace and reuse cases.
