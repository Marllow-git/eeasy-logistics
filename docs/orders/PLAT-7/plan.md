- **Status:** planned
- **Date:** 2026-11-01
- **Wave:** 0 (roadmap §1.1). **Depends on:** PLAT-6 (merged, PR #41); CHORE-1 (merged: Node 24, `util.parseEnv`, SWC builder).

## 0. Goal

Every admin and ledger-adjacent action, every cross-tenant call and every refusal the kernel already records lands as an immutable row in `core_audit_log`, written inside the business transaction when the action commits and on its own committed transaction when the request is refused, partitioned by month so two years of retention is a partition drop, readable per account on the staff surface and across accounts on the platform surface under the cross-tenant door, so that PLAT-10 to PLAT-13 can write their before-and-after rows into a frame that is already enforced and tested.

## 5. Exit criteria

- `core_audit_log` rows cannot be updated, deleted or truncated by any runtime role, directly or through a partition; proven by tests in both RLS lanes.
- Every cross-tenant call and every door refusal leaves exactly one row; a refused request's row survives its rollback.
- The three list operations return `AuditLogEntry` pages with stable cursors; a tenant never sees another account's rows.
- Partitions exist three months ahead after every migrate run; the worker drops partitions past the retention and audits each drop.
- The adversary pass finds no critical or high.

### 8.1 Skills, documents and versions consulted

### 8.2 Interpretations the lead should check

1. `tenant_isolation` on `core_audit_log` keeps the data §4.3 template (all commands, `USING` and `WITH CHECK`) instead of decision 2.1's "SELECT only": `AuditWriter.record()` writes through the tenant unit of work on `elx_app` (2.4), and with RLS on a SELECT-only policy would refuse that insert. UPDATE and DELETE stay impossible through the grants and the trigger; the `WITH CHECK` keeps a tenant to its own account.
2. Migration 0006 was generated by `drizzle-kit generate` (not `--custom`), then edited by hand, so the snapshot holds `core_audit_log` and a later generate does not try to create it; `--custom` writes no table into the snapshot (checked). The Drizzle schema file declares the parent for types; `occurred_at` is `mode: 'string'` (microseconds, for cursors).
3. Partition bounds are UTC month starts; the partition name is `core_audit_log_YYYYMM`. `core_ensure_audit_partitions` accepts 0 to 24 months ahead. `core_drop_audit_partitions_before(cutoff)` drops partitions whose upper bound is on or before `cutoff`, reads the bound from `pg_get_expr(relpartbound)`, skips a DEFAULT partition, and refuses (`22023`) a cutoff later than the first day of the month 24 months ago, so the retention cannot be shortened below two years from SQL either. No DEFAULT partition: a row outside the kept range fails its insert (fail closed) rather than landing in a partition the drop never reaches.
4. The owner can still `TRUNCATE` a single partition (statement triggers are not cloned to partitions; PostgreSQL 16 CREATE TRIGGER notes); the runtime roles hold no grant on any partition, which is the plan's line. The migrate runner calls `core_ensure_audit_partitions(3)` unconditionally in the version transaction (a folder without 0006 would now fail; there is none). Schema test: `core_audit_log` in `nullableAccountTables`, `appendOnlyTables` and `globalUniqueIndexes` (`(id, occurred_at)`, the partitioned key); the partition check covers every partition in `public`, not only those of append-only tables.
5. `withCommittedSideEffect(pool, fn)` is a new entry `@eeasy-logistics/db/committed` (a separate file, so dependency-cruiser can fence it: rule `committed-side-effects-only-in-audit` allows it only from `modules/kernel/audit/`, with a permitted fixture and a violation fixture). It is `withPlatformUnitOfWork(pool.db, fn, null)`: a new transaction on another pooled connection, its own frame, no `elx.account_id`. The `platform-pool-only-in-platform-code` rule now exempts that one package file, which wraps the platform pool.
6. Writer placement: the tenant `AuditLogRepository` lives in `modules/kernel/audit/`; the platform appender `PlatformAuditLog` lives in `modules/kernel/platform/` (the folder allowed to import `@eeasy-logistics/db/platform`), like the platform idempotency store. `record()` picks the tenant path when a tenant context is current (staff, driver, the door) and refuses an event whose `accountId` differs from it; otherwise it appends through the current platform unit of work with the event's account as given; outside both it throws. `recordCommitted()` throws without `DATABASE_URL_PLATFORM` (outside production only), so a refusal is never answered unaudited.
7. Door rows: `targetType` `account`. Refusals (`platform.cross_tenant.refused`; outcomes `reason_missing`, `reason_invalid`, `not_found`) carry `account_id NULL`, because the account may not exist (the FK would fail) and is not yet checked; the attempted id is `target_id` (`malformed` for a value that is not a UUID, never the raw value). Admitted calls (`platform.cross_tenant.accessed`) carry the account and `after: { operation, outcome: 'ok'|'failed', status }`; the merchant therefore sees platform access to its account in `listAuditLog`, not refused attempts. The row is written after the door transaction settles (it holds no connection then); if that write fails the request answers 500 and the data is not returned. The success status is the handler's own, else its `@HttpCode()`, else 201 for POST and 200 otherwise.
8. Redaction follows decision 2.5's key list literally; it is a substring match, so keys such as `shipping_fee` (`pin`) or `tokens_used` are redacted too. The lead may want word boundaries before PLAT-10 writes business before/after rows. Beyond 2.5: non-JSON values become JSON (Date to ISO, bigint to string, functions and `undefined` dropped, non-finite numbers null), nesting stops at 32 levels or a cycle (`[too_deep]`). `client_request_id` is folded into `after` after redaction.
9. `AuditEvent` replaced the PLAT-6 shape (`kind`, `actor`, `operation`, `outcome`, `at`); `LogAuditSink` is deleted. The PLAT-6 door tests now read the committed rows from the table instead of a recording sink (same cases, stronger assertions), and no longer delete their accounts afterwards (audit rows reference them and are never deleted).
10. `@CrossTenant()` takes an optional source (`{ from: 'path' | 'query', name }`, default the path's `account_id`); built in this item because the interceptor reads it; used by item C.
11. Cursors are signed (ADR-0029 "signed by the API", which decision 2.6 leaves out): `<base64url payload>.<base64url HMAC-SHA256>` under HKDF-SHA256 of the signing key with info `elx-cursor`, a key separate from the idempotency one. The binding hash covers the operation id, the filters (as the contract names them, `account_id` included on the platform operations) and the sort, not the limit. `k[0]` is PostgreSQL's text of `occurred_at` (microseconds, session offset), checked against a timestamp pattern before use. Any failure (format, signature, binding, expiry) is the same `400 validation_failed` on `/query/cursor`.
12. `ScopedRepository.findMany` gained an optional `{ orderBy, limit }` (a second `packages/db` change besides the committed helper; the plan named one): the tenant base had no ordered or limited read, and its transaction is private by design.
13. `created_from` is inclusive and `created_to` exclusive on `occurred_at`; the contract's default sort text (`-created_at`) is the contract's generic wording, the audit lists accept only `-occurred_at` (default) and `occurred_at`; anything else is `400` on `/query/sort`. `occurred_at` is answered as ISO 8601 UTC with microseconds.
14. Presenter: `actor_id`, `ip`, `user_agent` are omitted when NULL (the contract types them as non-null strings); a non-object `before`/`after` would be wrapped as `{ value }` (the writer stores objects). On the staff surface, rows whose actor is `platform_user` omit `ip` and `user_agent`: a merchant sees that platform staff acted, why and when, not from where. The platform surface shows everything.
15. `platformListAudit` without `account_id` is plain platform work and writes no audit row (no account is read); the contract still requires `X-Support-Reason` there (the ContractPipe enforces it). With `account_id` the door takes it from the query (`@CrossTenant({ from: 'query', name: 'account_id' })`); the handler also checks that the door's account equals the parsed query value. The handlers live in `modules/kernel/audit/` (the first kernel controllers in `src/`), registered by `KernelModule`.
16. Contract scenarios for the three operations (`packages/contracts/test/scenarios/`) expect `401`: no sign-in exists before PLAT-11, so they check the error shape only; PLAT-11 should turn them into signed-in `200`s.
