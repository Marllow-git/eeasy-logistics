Disjoint from the web orders.

## 0. Goal

A platform admin provisions an account in one call (name, locale, limits, modules, the owner's invitation) and nothing is ever created on first use; a super admin sets each feature's rollout mode and an admin enables flags per account, the kernel gate answers `feature_not_enabled` everywhere else and `Me.features` tells the web what to show; suspension pauses the account's outbox effects and refreshes and closure follows; platform staff are invited, re-roled and TOTP-reset by super admins under audit; and every cross-tenant read of members and audit rows lands as one audit row with the support reason, so that the first pilot merchant can exist without a database edit (ADR-0006, K-1) and wave 0 can close.

## 5. Exit criteria

- An account exists only through `platformProvisionAccount`; it turns `active` only when its owner accepts; the owner's mail reaches Mailpit.
- K-6 holds for every mode and flag combination at the gate and in `Me.features`; only a super admin changes a rollout mode.
- A suspended account cannot refresh a session, its external outbox effects wait, and reactivation restores both; closure is final and audited.
- Every cross-tenant read leaves one audit row with the support reason and none without.
- Super-admin rights come only from a super admin; nobody changes or resets themselves; the last super admin is protected.
- No secret, token or TOTP material in any response, log, audit row or mail; the adversary pass finds no critical or high.

### 8.2 Notes

Leg 1 (items A to D):

1. **Migration number and shape:** generated as `0015_core_rollout` on main a16fefa; INT-4 merged its `0015_core_push_tickets` first (167845f), so the rebase regenerated this one as `0016_core_rollout` with `drizzle-kit generate --name=core_rollout` (never a rename: the generated SQL was byte-identical, the new snapshot chains to INT-4's) and ported the hand-written header, revoke, policies and seed. The plan body (header, 2.1, item A) still says 0015: the lead renumbers it. drizzle-kit output from `schema/rollout.ts`, with the header, the `elx_app` revoke, the two policies and the seed appended by hand. `core_feature_flags` is keyed by its primary key `(account_id, feature_key)` (the unique pair of 2.1; it also leads with `account_id`, so no separate index), has `created_at`/`updated_at` and `version >= 1` beyond 2.1's list, and its `feature_key` is a foreign key to `core_rollout_modes` (named `core_feature_flags_feature_key_fk`: drizzle-kit's generated name is 64 bytes and PostgreSQL would truncate it), so no flag can name an unregistered feature. No CHECK lists the keys: a later module adds its key with a seed row, not a constraint change.
2. **Seed and registry:** `modules/kernel/features/feature-keys.ts` holds `featureKeys = ['delivery', 'wms']` (§7 #1); the migration seeds both in `allowlist` with `updated_by` NULL, `ON CONFLICT DO NOTHING`; `rollout-table.test.ts` fails when the seeded rows and the registry differ. Grants: `elx_app` SELECT only on both tables, `elx_platform` all four on both.
3. **Activation hook (2.3):** `provisioning/account-activation.ts` `AccountActivation.onOwnerAccepted(tx, membership, audit, facts)` runs in `StaffSignIn.acceptInvitation` right after its `core.invitation.accepted` row, in the same identity transaction: one `UPDATE … WHERE status = 'provisioned'` (`version + 1`), so only the first owner acceptance moves the account and a non-owner acceptance never does (tested); audit `core.account.activated` as the accepting user with `before`/`after` status and the membership id.
4. **One provisioning transaction (2.2):** the account, its flags, the owner's invitation and mail, the event and the audit row commit together in the request's platform transaction (8.1 #1). `currentProvisioning()` in `platform/provisioning.repository.ts` hands the service the request's platform unit of work, since only `modules/kernel/platform/` may import `@eeasy-logistics/db/platform` (depcruise `platform-pool-only-in-platform-code`).
