# PLAT-13 · Provisioning, rollout and suspension

- **Status:** registered 2026-11-02 (PLAT-12 merged through PR #89); brief at once.
- **Date:** 2026-11-02
- **Wave:** 0 (roadmap §1.1, critical path). **Depends on:** PLAT-7 (merged, PR #61), PLAT-8 (merged, PR #63), PLAT-11 (merged, PR #83), PLAT-12 (merged, PR #89). **Unblocks:** WEB-4, DEL-1 (the zone and coverage steps of the provisioning door), wave 0 exit.

Disjoint from the web orders.

## 0. Goal

A platform admin provisions an account in one call (name, locale, limits, modules, the owner's invitation) and nothing is ever created on first use; a super admin sets each feature's rollout mode and an admin enables flags per account, the kernel gate answers `feature_not_enabled` everywhere else and `Me.features` tells the web what to show; suspension pauses the account's outbox effects and refreshes and closure follows; platform staff are invited, re-roled and TOTP-reset by super admins under audit; and every cross-tenant read of members and audit rows lands as one audit row with the support reason, so that the first pilot merchant can exist without a database edit (ADR-0006, K-1) and wave 0 can close.

## 5. Exit criteria

- An account exists only through `platformProvisionAccount`; it turns `active` only when its owner accepts; the owner's mail reaches Mailpit.
- K-6 holds for every mode and flag combination at the gate and in `Me.features`; only a super admin changes a rollout mode.
- A suspended account cannot refresh a session, its external outbox effects wait, and reactivation restores both; closure is final and audited.
- Every cross-tenant read leaves one audit row with the support reason and none without.
- Super-admin rights come only from a super admin; nobody changes or resets themselves; the last super admin is protected.
- No secret, token or TOTP material in any response, log, audit row or mail; the adversary pass finds no critical or high.

## 6. Not in this order

Zones and coverage provisioning (`platformProvisionZone`, `platformProvisionCoverage`: DEL-1); the cross-tenant order and driver reads (DEL orders); ending driver shifts on suspension (DEL-5's consumer); API-key rejection on suspension (wave 4); the diagnose console (DEL-15); the console screens (WEB-4); gating any existing route with `@Feature` (the DEL and WMS orders do it as they ship); per-account export and deletion (wave 1 data order); read-only impersonation (identity §10 question 3); custom roles.

### 8.1 Deviations

1. **A second change to PLAT-11's code besides the activation hook (B):** `Invitations.createStaff(input, tx?)` takes an optional identity transaction and `identityTransactionOf(uow)` is extracted from `identityStore`, so the provisioning door can create the account and the owner's invitation in one transaction (2.2 says one platform transaction; `createStaff` opened its own, which cannot see the uncommitted account). Without `tx` the method behaves as before; PLAT-11's and PLAT-12's suites stay green.
2. **The gate reads the platform pool, not the app pool (C):** 2.1 grants `elx_app` SELECT on both tables "because the gate reads from the app pool", but `core_rollout_modes` has no `account_id` and no tenant repository can reach a platform table (`ScopedRepository` needs `account_id`; elx_app reads of platform tables do not exist in the codebase: PLAT-12 reads `core_accounts` on the platform pool, PLAT-10 `core_roles` too). The gate's table reads (`platform/features.repository.ts` `featureStoreOnPool`) run in one short platform transaction for the account the principal names, before the request's unit of work opens, mostly skipped by the Redis cache. The `elx_app` SELECT grants of 0016 stay (harmless, and ready for a later tenant read).
3. **`PlatformMe` gets no feature list (C):** 2.5 says `PlatformMe` gains the enabled keys, but the contract's `PlatformMe` has no `features` field (`user`, `permissions` only) and a platform user has no account to resolve K-6 for; adding a field would fail the contract tests (`undocumented_field`). `Me.features` (staff) is filled. The lead may add a contract field if the console needs the rollout state (it can read `platformListRolloutModes`).
4. **Feature labels not added (C):** 2.5 and 2.11 put two bilingual labels in a `packages/i18n` `platform` namespace, but that namespace lives in `apps/admin/messages` (ADR-0038; `packages/i18n/src/messages.ts`), a path of the WEB-2 order in flight and not of this plan. No API string needs them; WEB-4 adds them with the console screen (8.3).
5. **A third change to PLAT-11's code: the refresh order (E):** 2.7 revokes every staff family of a suspended account and 2.12 expects the member's refresh to answer `403 account_suspended`, but PLAT-11's `refreshVerdict` refuses a revoked row as `401 token_invalid` before it reads the account. A revoked row of the member's own active membership on a suspended account now answers `account_suspended`; every other revoked row (another surface, an ended membership, any other account state) stays `token_invalid`, and nothing is issued either way. It tells the holder of that account's refresh token only what the unrevoked token told them before. One unit case added; PLAT-11's cases unchanged and green.
6. **`Invitations.createPlatform(input, tx?)` (G):** like `createStaff` (#1), PLAT-11's platform invitation takes an optional identity transaction, so `platformInviteStaff` writes the user, the invitation, its mail and the door's audit row in the request's platform unit of work (one connection). Without `tx` it behaves as before (the bootstrap command and the test helper); PLAT-11's suites stay green.
