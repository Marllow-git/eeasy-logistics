- **Issue:** #90. **Merge danger:** one-way door (one migration: `core_push_tickets`). Blast radius: the worker gains the `push` queue and a receipts job; no producer exists yet, so nothing is sent until a DEL order writes `push` rows.

## 0. Goal

A Delivery consumer writes one `push` outbox row for a driver's devices and the worker delivers it through the Expo push service in batches, with localised title and body rendered on the server from a catalogue, payloads that carry ids only, tickets kept and receipts checked 15 minutes later so a device that unregistered stops receiving pushes through a hook DEL-4 registers, and a recorder stub that local and CI assert on, so that DRV-5 and the DEL orders only produce rows (ADR-0024, integrations §2.5, driver app §8.2).

## 1. Binding rules and ADRs

- AGENTS.md hard rules: side effects through the outbox (the kind `push` is one; no service calls Expo directly); config through `packages/config`; secrets never in code; Arabic and English for every string.
- ADR-0024 (outbox and queues per kind). ADR-0009 (push is a hint: offers and runs are also fetched by the app; an open breaker or a lost push delays, never loses, work). ADR-0021 (the driver app in the monorepo; catalogues shared through `packages/i18n`).
- `docs/architecture/integrations.md` §2.5 `PushSender` in full (methods, owner, Expo adapter with an access token and enhanced push security on, kind `push`, receipt polling as a scheduled worker job, 5 s per batch of up to 100, idempotency by the outbox row id in `data`, token invalidation on `DeviceNotRegistered`, breaker and degraded, in-memory recorder stub, credentials), §4.1 row `push` (supersede key `push:{driver_id}:{order_id}`; expired offers are dropped), §4.2 queue `outbox.push` (concurrency 4, batches of 100, 500 per second, 3 attempts at 10 s, 30 s, 2 min, dead after the last; `rate_limited(retry_after_s)` reschedules without an attempt), §4.3 supersede and staleness, §4.4 outcomes.
- `docs/architecture/driver-app.md` §8.2 "Push notifications" (Android channels `offers`, `run`, `cash`; payloads carry ids only plus a localised title and body rendered by the server in the driver's locale; no recipient name, phone or address; deep links `eeasydriver://offers/{offer_id}`, `eeasydriver://orders/{order_id}`, `eeasydriver://cash`, `eeasydriver://sync`; the app suppresses a push for an offer it already shows by id).
- `docs/architecture/data.md` §2.1 `del_driver_devices` (`push_token`; DEL-4's table; this order never reads it), `core_outbox`; §10 (a push token is personal data: never logged).
- `docs/research/eas-and-store-accounts-2026-11.md` (the EAS organisation and access token are OPS-3's owner inputs; nothing here depends on them except the production refusal of 2.6).
- Expo Push Service HTTP API, read 2026-11-02 (`https://docs.expo.dev/push-notifications/sending-notifications/`): `POST https://exp.host/--/api/v2/push/send` with a JSON array of up to 100 messages for one project, `Authorization: Bearer <access token>` when enhanced push security is on; tickets `{ status: 'ok', id }` or `{ status: 'error', details: { error } }` per message in order; `POST …/push/getReceipts` with up to 1,000 ids answers `{ data: { <id>: { status, details? } } }`, receipts available within 15 minutes and cleared after 24 hours; errors `DeviceNotRegistered` (ticket or receipt: stop sending to that token), `MessageTooBig`, `MessageRateExceeded`, `MismatchSenderId`, `InvalidCredentials`; request errors `TOO_MANY_REQUESTS` (600 per second per project), `PUSH_TOO_MANY_EXPERIENCE_IDS`, `PUSH_TOO_MANY_NOTIFICATIONS`, `PUSH_TOO_MANY_RECEIPTS`; retry 429 and 5xx with backoff, never a 400. No SDK: the API is three JSON calls (the Node SDK's six-connection throttle is the queue's concurrency and limiter here).
- Kernel in place: PLAT-8 `KindHandler`, `KindOutcome`, `ProviderFailure` (`rate_limited`, `unauthorised`, `permanent`, `transient`), the queue policies of §4.2 and `outbox-workers.ts`, `buildKindHandlers`, the Redis lock pattern of the system jobs (`otp-purge.ts`); PLAT-9 `messageTemplateTexts` and the parameter rules (`templates.ts`, adversary L-7: no line break, bounded lengths) as the pattern for a second catalogue; PLAT-14 `withPortSpan` (port `push_sender`, provider `expo` or `stub`), the metrics catalogue, the redacting logger; PLAT-4 config `secret()`, `resolveProvider` pattern of `MESSAGING_PROVIDER`.

## 5. Exit criteria

- A `push` outbox row reaches the recorder (local, CI) or Expo (staging) with title and body in the row's locale and a payload of ids only; a second delivery of the same row is a no-op for the app (`push_id`).
- A `DeviceNotRegistered` ticket or receipt reaches the invalidation registry exactly once per device; no token, title or body appears in any log, span or audit row.
- Rate limits reschedule without consuming an attempt; a malformed row is dead at once; receipts are checked after 15 minutes and tickets purged after 7 days.
- Production refuses to start without an explicit push decision.

## 6. Not in this order

Producers of `push` rows (DEL-2 offers, DEL-6 assignments, DEL-8 cash notices, DRV-6 sync prompts); the driver app's `expo-notifications` registration, channels and deep links (DRV-5); `del_driver_devices` and the token-clearing handler (DEL-4); a breaker in front of Expo (the queue's limiter and backoff cover §2.5 "push is a hint"; a breaker joins when a second push provider exists); gzip request bodies; the EAS organisation, access token and store accounts (OPS-3 inputs, OPS-1 configuration).
