# PLAT-8 · Outbox, relay and worker queues

- **Status:** planned; brief after PLAT-7 closes (both touch `apps/api`, `packages/db`, `packages/config`)
- **Date:** 2026-11-01
- **Wave:** 0 (roadmap §1.1). **Depends on:** PLAT-6 (merged, PR #41); Q-42 ruled 2026-11-01 (BullMQ on Valkey, ADR-0036 stands). PLAT-7 (audit writer) is a build dependency for replay audit rows, so this order starts after PLAT-7 merges.
- **Lead:** architecture lead. **Executor:** `executor-api` (Opus), own worktree, native stack scratch databases and a scratch Valkey or Redis port. **Adversary:** yes (cross-tenant outbox reads and replay, payloads holding private data, the single-leader relay, dead-letter handling).
- **Issue:** #59. **Merge danger:** one-way door (migration 0007 with three tables; the worker gains the relay and the queues). **Legs:** three (A–C, D–F, G–H).

## 0. Goal

Every side effect leaves the business transaction as an outbox row and nothing else: a single-leader relay moves due rows into one BullMQ queue per kind on Valkey in per-aggregate order, workers execute them through kind handlers with per-kind retries and write the outcome back to the row, internal consumers deduplicate on receipts and park out-of-order events, dead rows are listed and replayed by platform staff under audit, and old rows are pruned, so that PLAT-9 onward add handlers and consumers into a frame where at-least-once delivery, ordering and tenancy are already enforced.

## 5. Exit criteria

- A business change and its outbox row commit or roll back together; the envelope cannot be changed afterwards.
- Exactly one relay leader at a time; rows leave in per-aggregate order; a lost Redis job is recovered by the sweeper.
- Outcomes are on the row; Redis holds only job ids.
- Internal consumers are idempotent on receipts and park out-of-order events.
- Dead rows are listed and replayed under audit by platform staff; pruning keeps the windows of data §5.2.
- CI runs on Valkey; the adversary pass finds no critical or high.

### 8.2 Interpretations the lead should check

1. **Receipts and dead letters are nullable-account tables**, like `core_outbox`: their account mirrors the event's, and a platform-only `internal_event` has none. All three are listed in `nullableAccountTables` with the template policies; `(supersede_key)` and `(consumer, event_id)` are in `globalUniqueIndexes` (keys embed the aggregate's UUID; event ids are UUIDv7). Data §2.4 names only the audit log and idempotency keys as nullable; a data-doc amendment may be wanted.
2. **NOTIFY is a table trigger**, not a statement in the writer: `core_outbox_notify()` `AFTER INSERT FOR EACH STATEMENT` runs `pg_notify('elx_outbox', txid_current()::text)`. The tenant repository base exposes no raw SQL (PLAT-6 M-1), so a writer-issued `pg_notify` would have needed a new door in `packages/db`; the trigger also wakes the relay for SQL-side inserts. The payload is the transaction id only (no row data): parallel test suites tell their own commit apart by it.
3. **Ids are a per-process monotonic UUIDv7** (`nextOutboxId`, 12-bit counter, RFC 9562 method 1) and the relay orders a scope by `(sequence, id)`: several events of one change share `sequence` and come from one transaction (one process), so their ids keep the write order; across changes `sequence` decides. `packages/db` `uuidv7()` is random within a millisecond and would not do this.
4. **The writer also takes a platform unit of work** and then writes `account_id` NULL (platform-only effects, plan 2.1); a tenant unit of work (staff, driver, the cross-tenant door) writes its context account. An `accountId` in the entry is never read (tests pass one through a cast on both paths). `correlation_id` defaults to the unit of work's request id when that is a UUID; `causation_id` defaults to NULL. Entries are checked (catalogue type, positive versions, UUID aggregate, object payload) and refused with `OutboxEntryError`.
5. **`listenOnPlatformPool` in `packages/db/platform`**: plan 2.2 says `packages/db` gains nothing, but the relay's LISTEN needs the postgres.js client, which only `packages/db` may import (rule `database-driver-only-in-packages-db`). The helper uses the pool client's dedicated listener connection; importable only where `/platform` is.
6. **The relay's select uses a `LEFT JOIN core_accounts`**: plan 2.3's `JOIN … ON a.id = o.account_id OR o.account_id IS NULL` pairs a NULL-account row with every account. The relay lives in `src/worker/system/outbox-relay.ts` because the platform pool may be imported only there or in `modules/kernel/platform/`; the registry and queues are in `modules/kernel/outbox/`.
7. **Kinds without a handler are filtered in the select** (so they never fill a batch and starve handled kinds) and counted by the sweeper once a minute as `outbox_rows_without_handler` (a log line and `relay.stats`; there is no metrics exporter yet, PLAT-14). The production registry is empty in leg 1, so the deployed relay moves nothing until leg 2 registers `internal_event` and `storage_lifecycle`; the tests register a test-only handler for `carrier_call`.
8. **Ordering scope**: a handler's `orderingKey(row)` refines `(kind, aggregate_id)`; the relay reads only the envelope columns (never the payload) and compares open rows of the same kind and aggregate. A scope wider than the aggregate (integrations §4.1 `channel_publish` "per connection") needs more than this and is the INT order's to add.
9. **Lock timings follow integrations §4.4 and plan 2.3** (TTL 10 s, renewal every 3 s, relaying stops 1 s before the TTL could lapse; sweeper after 5 minutes), not data §5.2's older 30 s / 10 s / 10 minutes. The data doc may need the same amendment.
10. **Enqueue before commit**: jobs are added inside the batch transaction; if the commit then fails, a job exists for a row still `pending`, and the next batch's add is a no-op by `jobId`. Leg 2's worker must accept a job whose row is `pending` or `enqueued` (it re-reads the row) and should keep completed jobs no longer than the row needs, since a retained job id blocks a re-add.
