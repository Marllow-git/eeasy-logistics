- **Status:** planned; brief after PLAT-10 closes (both touch `apps/api`, `packages/db`, `packages/config`)
- **Date:** 2026-11-01
- **Wave:** 0 (roadmap §1.1). **Depends on:** PLAT-8 (merged, PR #63); Q-27 ruled 2026-11-01 (A-22: eeasynew's verified WhatsApp business and provider on a new number, our own templates and credentials; the provider name is still owed by the owner).
- **Lead:** architecture lead. **Executor:** `executor-api` (Opus), own worktree, native stack scratch databases, Redis, the `whatsapp-stub` and Mailpit of the native stack. **Adversary:** yes (OTP codes, phone numbers, credentials encryption, rate budgets, opt-out, the provider webhook secret).

WEB orders in flight touch none of these except `packages/i18n` catalogues (a different namespace file; no conflict expected).

## 0. Goal

Every outbound message leaves the system as a `message` outbox row handled by one `MessageSender` port: OTP codes for drivers and staff second factors reach a phone over WhatsApp with the code encrypted at rest and the row deleted one hour after sending, invitations and password resets reach an inbox through the mail adapter, recipient messages (wave 1) will reuse the same port with quiet hours, caps and opt-out already enforced, and the stub makes all of it testable without a provider, so that PLAT-11 can build sign-in doors on a delivery frame that already meets ADR-0037 and data §10.

## 5. Exit criteria

- An OTP requested at the test door arrives at the stub with the code, is never stored or logged in clear, verifies once, and its row and challenge are gone one hour later.
- Invitation and reset mails arrive in Mailpit in both languages.
- Quiet hours, caps, opt-out and the budget skip recipient templates and never OTP; `MESSAGING_DISABLED` and the open breaker behave per doc 9 §2.4.
- The adversary pass finds no critical or high.

2. **`MESSAGING_STUB_URL`** (not in 2.9): the stub adapter needs the stub's address, and the ci profile publishes a random port. 5. **Breaker:** five consecutive transient failures (network, timeout, 5xx; not 429, 401/403 or other 4xx) open it for 30 s, then one trial (half-open). Its open state is shared as the Redis key `elx:breaker:messaging:<provider>` (PX = the window), which the OTP door reads; a Redis failure never changes a send's own outcome, and the door treats an unreadable key as closed (fail open, like the rate limiter). Threshold and window are defaults of this order, not doc values.
6. **Mail adapter:** plain-text bodies; the outbox row id becomes the `Message-ID` (`<id@eeasy-logistics>`), so a resend after a timeout carries the same id; recipients are a single bare address (no display name, no comma, no line break); `requireTLS` in staging and production; SMTP `EAUTH` parks, 5xx is permanent, everything else transient. The mail adapter has its own breaker (`smtp`), separate from the WhatsApp one the door reads.
7. **CI:** `.github/workflows/pr.yml` (api-test lanes) now exports `MESSAGING_STUB_URL`, `MAIL_SMTP_URL`, `MAIL_FROM` (from `.env`) and `MAILPIT_URL` from the ci profile's published ports; `MAIL_FROM` in `.env.example` is double-quoted because CI and `tools/native-stack.sh` source the file in bash. Not in the plan's path list. `MAILPIT_URL` is read by the test helper `mailpitUrl()` only (default `http://127.0.0.1:8025`), never by application code.

9. **Hashing:** `code_hash` = HMAC-SHA256(HKDF-SHA256(credentials key, info `elx-otp`), "<challenge id>:<code>"), so a hash is bound to its row. New codes use the active key; verification tries every configured key with no early exit (a rotation inside the five minutes does not invalidate a sent code). Rate-limit keys hold no phone: `phone:<HMAC pseudonym>` under the same key family.
10. **Order of checks on request** (amended by lead review round 1, finding 1): E.164 (`400 validation_failed` at `/body/phone` for an unparseable phone, which leaks nothing about accounts), then availability (`503`), then in one platform transaction an advisory lock on (phone, purpose), the cooldown (`429 rate_limited` with `Retry-After` = seconds left), then the address budget (20/h) and the phone budget (5/h), then the challenge and the outbox row. An availability or cooldown refusal charges no budget, so neither can spend a user's hourly quota; a budget refusal rolls the transaction back. Budgets are fixed windows of one hour in Redis through the PLAT-6 limiter's `charge(name, identity)`; like every PLAT-6 budget they fail open when Redis is down (owner question 1 of PLAT-6), the database cooldown does not.
11. **Verification:** only the newest challenge of (phone, purpose) counts, so a code replaced by a resend stops working; it is locked `FOR UPDATE`; expiry is judged on the database clock; a wrong or malformed code (not six digits) adds one attempt; at five the challenge is dead even for the right code; an unparseable phone or no challenge runs the same HMACs and answers `otp_invalid`. Success sets `consumed_at` and returns the E.164 phone for PLAT-11 to look the driver up.
12. **Outbox row of an OTP:** a platform-only row (`account_id` NULL: the challenge precedes the account), type `core.otp_challenge.created` (added to the code catalogue `domainEventTypes`; domain model §6.3 lists business events only and is unchanged), aggregate `otp_challenge` = the challenge id, kind `message`, supersede key `otp:<E.164>:<purpose>` as 2.4 says (the phone is in `to` anyway; the platform metadata list hides `supersede_key`), payload `{ channel, template, to, locale, challenge_id, params: { code: { encrypted: <base64 blob> } } }`. The leg 2 handler decrypts with the context `core_otp_challenges:<challenge_id>`. In leg 1 no `message` handler is registered, so the relay leaves these rows `pending`.
13. **Grants of 0009:** `elx_app` gets nothing (the doors run on the platform pool); `elx_platform` keeps SELECT, INSERT, UPDATE, DELETE from the default privileges, DELETE for the leg 2 purge.
14. **503 on the door** (amended by lead review round 1, finding 2): availability comes from the senders registry the API builds at boot (`MESSAGE_SENDERS`, `createMessageSenders`): `503` unless a WhatsApp sender exists in this build (so `meta`, `bsp` and the stub without `MESSAGING_STUB_URL` all answer 503 until the leg 2 adapter), messaging is not paused (`MESSAGING_DISABLED`) and that sender's breaker is closed in the shared Redis state (#5); without `REDIS_URL` the breaker is not consulted. Building the senders in the API also makes the stub refuse to boot outside local and ci there.
15. **Missing configuration:** without credentials keys or the platform pool the OTP service answers `500 internal_error` and the API logs one warning at boot (production requires both).

16. **Door wiring is test-only:** the probe controller lives in `test/integration/otp-door.http.test.ts` and binds the generated `driverRequestOtp` and `driverVerifyOtp` entries (`core.auth.anonymous`, so `@Public()` passes `OperationRoutesCheck`); the shipped API has no OTP route until PLAT-11 (the dist boot answers 404). The kernel gains `ClientIp` (`request/client-ip.ts`), a parameter decorator for `request.ip`, (with a reasoned `eslint-disable` for the restricted `createParamDecorator` import, as `contract-pipe.ts` has), because controllers outside the kernel may not read the raw request and PLAT-11's door needs the address for the per-address budget.
17. **What is not `otp_invalid`:** a body outside the contract (a code that is not six digits, a missing `device`) is `400 validation_failed` from `ContractPipe` before the service runs, and an unparseable phone on the request door is `400` at `/body/phone`; neither depends on whether an account exists. On verification an unparseable phone answers `otp_invalid` before any transaction opens (lead review round 1, finding 3). Every verification of a well-formed body that fails is `401 otp_invalid` with the same `code` and `message`.

23. **Outcome mapping:** 2xx `ok:true` → `done` (the engine's state is kept for item G's columns); 401/403 → `unauthorised` (parked an hour without an attempt, since a wrong key or secret is a configuration fault, not a dead message; 2A.1 says refusals are dead, read here as the 4xx schema and binding refusals); 429 → `rate_limited`; 5xx, network and timeout → `transient` with status `ENGINE_UNAVAILABLE`, which the handler turns into a retry that consumes no attempt (2A.1), bounded by the outbox's 50 deferrals; any other 4xx (422 `BINDING_MISMATCH`, `EXPIRY_MISMATCH`, 409, 413) → `dead` with the engine's code, unless `retryable: true`. 24. **Resend check:** a row with `attempts > 0` or `deferrals > 0` first sends `message.status`; an engine that holds the id (and has not ended it `failed`/`expired`) means `done` without a second send; otherwise the send goes out under the same idempotency key with a fresh nonce, which the engine dedupes anyway. A failed status call falls through to the send.
25. **Spans and logs (PLAT-14, merged meanwhile):** every engine call runs in `withPortSpan({ port: 'message_sender', method: 'send_template' | 'status', provider })` (the helper requires snake case); `messages_sent_total` and `messages_skipped_total` are counted; log lines carry template, channel, provider, state and the phone's last two digits only, never the body or code. 26. **Skip reasons:** `done` gains an optional `skipped` reason, stored in `last_error` as `skipped: <reason>` the way a superseded row's reason is (integrations §5.5 "done, reason opted_out"); a sent row's `last_error` stays null.
27. **Handler lifecycle:** the worker builds the handler only when this build has a WhatsApp or mail sender; it owns a Redis client for the shared breaker state, closed through a new optional `KindHandler.close()` that `startWorker` calls after the queues drain. Until item G the resolver is platform-only: OTP and platform rows use the platform instance, an account's row is `no_sender`.
28. **Callback path:** the door is `POST /internal/whatsapp/v1/callbacks`, not 2A.2's `/internal/whatsapp/callbacks`: the engine posts to its configured base plus the compiled constant `CALLBACK_PATH = '/internal/whatsapp/v1/callbacks'` and signs that path (eeasynew `services/whatsapp-engine/src/callbacks/poster.ts`), so any other path would never be reached.
29. **Reading the body last:** the JSON parser skips exactly that path (`configureHttp`), and the door verifies steps 1 to 6 from the headers before it reads the stream, bounded by the declared length (a missing `Content-Length` is 413, as contract §2.3 step 1 says "present"). Nest's `rawBody` option was not used: it needs the global parser, which reads every body before any check (Context7, NestJS "Raw body"). The controller reads `@Req()` with a reasoned `eslint-disable` (the door is not a contract operation). Out-of-surface paths carry no rate-limit budget (PLAT-6 `budgetFor`), so the door is not throttled; its cost before the HMAC is header parsing only.
30. **Answers:** 413 `REQUEST_TOO_LARGE`, 401 with the contract's auth classes, 422 `SCHEMA_INVALID` or `BINDING_MISMATCH`, 400 `UNKNOWN_CALLBACK` for a kind outside the four, else `200 {"ok":true}`. The body is `{ ok: false, error: { code } }`, nothing more (contract §2.3 disclosure).
31. **Binding:** the instance decides the account, from our tables: the configured platform instance is engine account 1 with no account; any other instance is looked up in `core_messaging_senders`. The callback's `eeasy_account_id` must equal that mapping, and a `message.status` must name a row of the same account, else 422 and nothing applied. A callback of an instance we do not know is acknowledged and ignored (never 422: a refused `connection.event` makes the engine park that sender).
32. **Dedupe:** the nonce is reserved in its own committed statement before the body is used (step 8); the `callback_id` is then written onto that nonce row in the transaction that applies the callback, guarded by its unique index, so a redelivery (fresh nonce, same `callback_id`) is acknowledged and not applied, and a failed application releases the id for the engine's retry. Nonce rows (and so the dedupe memory) live 24 h; the engine's retries span about 24 h and every application is monotonic anyway.
33. **Message state:** `provider_state`/`provider_updated_at` on `core_outbox` (delivery-state columns, outside the envelope trigger), applied by rank (accepted < queued, held, paused < sending < sent, failed, expired, suppressed < delivered < read; nothing leaves a terminal failure, equal in-flight ranks by time). A status for a row that is gone (OTP rows are purged after an hour) is acknowledged. `failed` and `expired` are logged with the engine's error class; the row's own outbox status is not changed.
34. **Opt-out from the engine:** `suppression.changed` of an account's sender adds or removes `(account, phone)` with source `provider`; on the platform instance it is acknowledged and ignored (opt-out never blocks OTP). `OptOutList` (plan 2.7) ships in this item rather than H because the door feeds it; its words are the ADR-0041 union, matched case-insensitively with the Arabic alef forms folded (`إلغاء` = `الغاء`). Migration 0010 therefore lands with 0011 in this item, and it also holds `core_messaging_usage` (plan 2.8: a durable monthly counter rather than a Redis key, so a budget survives a Redis flush).
35. **Senders and the account id:** `core_messaging_senders` keeps one sender per account (PK `account_id`, `sender_instance_id` globally unique, as the engine binds an instance to one account); the engine supports several numbers per account, which a later linking order can add. `core_accounts.engine_account_id` (bigint, unique, `>= 2`) comes from `core_accounts_engine_account_id_seq` (MINVALUE 2; `elx_platform` USAGE, `elx_app` nothing), allocated by the resolver's first route for the account with a guarded UPDATE. `connection.event` updates the sender's `status` in `status_at` order; the platform instance has no row, its state is logged and counted only. `needs_relink` and `banned` count `messaging_sender_alerts_total{event, sender}` (new catalogue entry) with two alert rules in `observability/alerts.yaml` (platform: page in 5 min; account: warn); `breaker_open` loses its `pending` because `BreakerSender` now sets `integration_breaker_state`.
36. **Grants:** `elx_app` keeps SELECT on the opt-out, usage and sender tables (under the template policies) and loses the writes; it has no grant on the nonce table. All writes run on the platform pool (the worker and the door).
