## 0. Goal

Every outbound message leaves the system as a `message` outbox row handled by one `MessageSender` port: OTP codes for drivers and staff second factors reach a phone over WhatsApp with the code encrypted at rest and the row deleted one hour after sending, invitations and password resets reach an inbox through the mail adapter, recipient messages (wave 1) will reuse the same port with quiet hours, caps and opt-out already enforced, and the stub makes all of it testable without a provider, so that PLAT-11 can build sign-in doors on a delivery frame that already meets ADR-0037 and data §10.

### 8.2 Interpretations the lead should check

1. **Scope change from the coordinator (owner input, 2026-11-01):** WhatsApp sending will go through eeasynew's `whatsapp-engine` service (an admin links a number for platform and OTP messages; merchants may link their own). Leg 1 therefore builds the `MessageSender` port, the stub adapter and the mail adapter only; the Meta Cloud API adapter and the BSP slot of 2.1 are **not built**, and `MESSAGING_PROVIDER` keeps its values (`stub`, `meta`, `bsp`). The port keeps doc 9 §2.4's method shape and is reached through `MessageSenders.senderFor(accountId | null)`, which returns the platform adapter for every account today, so per-account linking can slot in under the amended plan. `MESSAGING_PHONE_NUMBER_ID` (2.9) is Meta-specific and is not added; `MESSAGING_WEBHOOK_SECRET` and `MESSAGING_TEMPLATE_NAMESPACE` are.
2. **`MESSAGING_STUB_URL`** (not in 2.9): the stub adapter needs the stub's address, and the ci profile publishes a random port. It is a local-and-ci-only variable (refused in staging and production like `DATABASE_URL_ADMIN`), and the stub adapter itself refuses to be built outside `local` and `ci`. The existing PLAT-4 rule (production refuses `MESSAGING_PROVIDER=stub`) is unchanged; staging still accepts the selector value, but cannot reach a stub.
3. **Mail in production:** `MAIL_SMTP_URL` and `MAIL_FROM` are required for both the `api` and `worker` roles (the list is shared); `MAIL_FROM` refuses line breaks and malformed addresses (header injection). No TLS scheme rule: `smtp://` with STARTTLS is legitimate.
4. **`503 messaging_unavailable` on `driverRequestOtp`:** added to errors.md §1 (additive) and declared on the operation in `driver.yaml` (one response line and the description), so the generated client knows it; not in the plan's path list.

5. **Breaker:** five consecutive transient failures (network, timeout, 5xx; not 429, 401/403 or other 4xx) open it for 30 s, then one trial (half-open). Its open state is shared as the Redis key `elx:breaker:messaging:<provider>` (PX = the window), which the OTP door reads; a Redis failure never changes a send's own outcome, and the door treats an unreadable key as closed (fail open, like the rate limiter). Threshold and window are defaults of this order, not doc values.
6. **Mail adapter:** plain-text bodies; the outbox row id becomes the `Message-ID` (`<id@eeasy-logistics>`), so a resend after a timeout carries the same id; recipients are a single bare address (no display name, no comma, no line break); `requireTLS` in staging and production; SMTP `EAUTH` parks, 5xx is permanent, everything else transient. The mail adapter has its own breaker (`smtp`), separate from the WhatsApp one the door reads.
7. **CI:** `.github/workflows/pr.yml` (api-test lanes) now exports `MESSAGING_STUB_URL`, `MAIL_SMTP_URL`, `MAIL_FROM` (from `.env`) and `MAILPIT_URL` from the ci profile's published ports; `MAIL_FROM` in `.env.example` is double-quoted because CI and `tools/native-stack.sh` source the file in bash. Not in the plan's path list. `MAILPIT_URL` is read by the test helper `mailpitUrl()` only (default `http://127.0.0.1:8025`), never by application code.
8. **Dependencies:** `nodemailer` 10.3.1 (2026-10-29, ships its own types) and `libphonenumber-js` 1.13.15 (2026-10-08), both past the three-day minimum. `pnpm install` refused to re-resolve because the driver's locked `@expo/metro-runtime` 58.0.16 and `@expo/log-box` are younger than three days; the install ran once with `--config.minimum-release-age=0` and the lockfile diff was checked to add only these two packages (17 lines, nothing else moved). `pnpm audit --audit-level moderate` exits 0.

9. **Hashing:** `code_hash` = HMAC-SHA256(HKDF-SHA256(credentials key, info `elx-otp`), "<challenge id>:<code>"), so a hash is bound to its row. New codes use the active key; verification tries every configured key with no early exit (a rotation inside the five minutes does not invalidate a sent code). Rate-limit keys hold no phone: `phone:<HMAC pseudonym>` under the same key family.
10. **Order of checks on request:** E.164 (`400 validation_failed` at `/body/phone` for an unparseable phone, which leaks nothing about accounts), then the address budget (20/h), the phone budget (5/h), availability (`503`), then in one platform transaction an advisory lock on (phone, purpose), the cooldown (`429 rate_limited` with `Retry-After` = seconds left), the challenge and the outbox row. So the budgets are charged even when the door answers 503 (doc 9 §2.4: "budgets still apply") and a cooldown refusal also spends the phone budget. Budgets are fixed windows of one hour in Redis through the PLAT-6 limiter's new `charge(name, identity)`; like every PLAT-6 budget they fail open when Redis is down (owner question 1 of PLAT-6), the database cooldown does not.
11. **Verification:** only the newest challenge of (phone, purpose) counts, so a code replaced by a resend stops working; it is locked `FOR UPDATE`; expiry is judged on the database clock; a wrong or malformed code (not six digits) adds one attempt; at five the challenge is dead even for the right code; an unparseable phone or no challenge runs the same HMACs and answers `otp_invalid`. Success sets `consumed_at` and returns the E.164 phone for PLAT-11 to look the driver up.
12. **Outbox row of an OTP:** a platform-only row (`account_id` NULL: the challenge precedes the account), type `core.otp_challenge.created` (added to the code catalogue `domainEventTypes`; domain model §6.3 lists business events only and is unchanged), aggregate `otp_challenge` = the challenge id, kind `message`, supersede key `otp:<E.164>:<purpose>` as 2.4 says (the phone is in `to` anyway; the platform metadata list hides `supersede_key`), payload `{ channel, template, to, locale, challenge_id, params: { code: { encrypted: <base64 blob> } } }`. The leg 2 handler decrypts with the context `core_otp_challenges:<challenge_id>`. In leg 1 no `message` handler is registered, so the relay leaves these rows `pending`.
13. **Grants of 0009:** `elx_app` gets nothing (the doors run on the platform pool); `elx_platform` keeps SELECT, INSERT, UPDATE, DELETE from the default privileges, DELETE for the leg 2 purge.
14. **503 on the door** also when `MESSAGING_DISABLED=true` or no provider is configured (plan 2.5 names only the open breaker): a code that will be superseded unsent should not be promised with a 202. The breaker state is read from Redis (#5); without `REDIS_URL` only the disabled and no-provider cases answer 503.
15. **Missing configuration:** without credentials keys or the platform pool the OTP service answers `500 internal_error` and the API logs one warning at boot (production requires both).

16. **Door wiring is test-only:** the probe controller lives in `test/integration/otp-door.http.test.ts` and binds the generated `driverRequestOtp` and `driverVerifyOtp` entries (`core.auth.anonymous`, so `@Public()` passes `OperationRoutesCheck`); the shipped API has no OTP route until PLAT-11 (the dist boot answers 404). The kernel gains `ClientIp` (`request/client-ip.ts`), a parameter decorator for `request.ip`, (with a reasoned `eslint-disable` for the restricted `createParamDecorator` import, as `contract-pipe.ts` has), because controllers outside the kernel may not read the raw request and PLAT-11's door needs the address for the per-address budget.
17. **What is not `otp_invalid`:** a body outside the contract (a code that is not six digits, a missing `device`) is `400 validation_failed` from `ContractPipe` before the service runs, and an unparseable phone on the request door is `400` at `/body/phone`; neither depends on whether an account exists. Every verification of a well-formed body that fails is `401 otp_invalid` with the same `code` and `message`.
18. **Verify's 200 body** in the probe is `{}` (every `DriverSession` field is optional); PLAT-11 returns the tokens, driver and device.
