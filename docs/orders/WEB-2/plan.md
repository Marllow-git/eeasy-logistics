## 0. Goal

A merchant staff user signs in on the web in Arabic or English, passes the phone second factor or enrols it, picks an account, accepts an invitation, resets a password and re-enrols through an emailed link; a platform user signs in to the console with password and TOTP, enrolling with a QR code on first use; sessions stay alive without the user noticing through the proxy on navigations and the single-flight fetch wrapper in the page; every page carries the security headers of web §3.6; and a session that ends sends the user to sign-in with the page they wanted, so that WEB-3 and WEB-4 build screens on a working session instead of a placeholder.

## 5. Exit criteria

- Every `(auth)` route of web §1 for wave 0, plus `/second-factor/enrol/[token]`, completes its main path in the census in `ar` and `en` against the real API.
- A navigation with an expired access cookie and a valid refresh cookie renders without a sign-in; an in-page `401 token_expired` is retried once after one refresh per browser.
- Every write carries `X-EL-Client: web`; every page carries the headers of web §3.6; no token, code, secret or URI is in a URL, a log line or an analytics event.
- `next` never leaves the origin; a rejected refresh lands on `/sign-in?next=`.
- The platform console signs in only with password and TOTP; enrolment shows the QR once.
- First-load budgets hold for the `(auth)` class; the adversary pass finds no critical or high.

## 6. Not in this order

Edge routing in production (OPS-1); the `Can` component and route manifest (WEB-3); the "Acting on account" banner and `X-Support-Reason` (WEB-4); the recipient pages and the embed path (DEL and wave 2 orders); the Hudhud or map CSP sources (WEB-7); `useEventStream` (WEB-5 or the dispatch order); a form library (WEB-3 decides); platform staff invitation screens beyond accept (WEB-4); read-only impersonation.

### 8.2 Interpretations and deviations the lead should check

1. **`proxy.ts` exports `config`, not `proxyConfig`** (plan 2.2 and §1 quote the skill): Next.js 16.4.3's bundled `proxy.md` and its build (`get-page-static-info.js`, `extractExportedConstValue(ast, 'config')`) read `config`; a `proxyConfig` export would be ignored and the proxy would run on every path, assets included.
2. **The proxy also refreshes on App Router navigations** (a request with the `RSC` header and no `Next-Router-Prefetch`), not only on `Sec-Fetch-Dest: document`: a `<Link>` navigation after 15 idle minutes would otherwise reach the `(merchant)` layout's `getMe` with an expired token and send a user with a valid refresh cookie to sign-in. Prefetches never refresh. The two-tab race web §3.2 names is covered by the API's 30 s reuse grace (PLAT-11 2.6). Deviation from 2.2's "not an RSC fetch"; the lead may prefer the plan's narrower rule.
3. **No refresh cookie, no redirect in the proxy**: 2.2 refreshes only when the refresh cookie is present; without it the request passes and the layout's `getMe` 401 sends the user to sign-in (2.3). A signed-in user on `/sign-in` is judged by the unverified `exp` of the access cookie; `/sign-in?reason=ended` clears both cookies (`Max-Age=0`, the API's attributes) so a token the API refuses cannot bounce the user between `/sign-in` and a page.

#### Fix round 1 (adversary M-1, M-2, L-1 to L-6)

44. **L-3 accepted, not fixed here**: the proxy forwards the client's `X-Forwarded-For` and `User-Agent` verbatim on its refresh call (the API's reuse grace compares the agent, #9), and the CSP sink keys its budget on the last `X-Forwarded-For` entry; both trust the edge. That chain is OPS-1's edge contract: the edge pins `Host` to the public hostnames, sets `X-Forwarded-For` (overwrite, or append exactly one hop) consistently with the API's `TRUST_PROXY_HOPS`, and prefers its canonical client-address header. Recorded as one line in the root README "Web sessions and headers" ("Edge contract for OPS-1").
45. **M-1** (`ReSignInDialog`, `SessionProvider`): the dialog's steps sit in an inner component keyed by an opening counter that moves on every change of `open`, so step, password, code and error start afresh in both directions, and an answer that lands after the close is dropped; the password leaves state when it is sent. The provider calls the app's `reauthentication(fetcher, me)` afresh at each opening and holds an inert pair of steps while the dialog is closed, so the `challengeId` inside `staffReauthentication` and `platformReauthentication` (closure state) dies with the dialog; the two wrappers needed no change of their own. Tests: the dialog (both directions) and the provider (factory called again after a dismissal, password step and an empty field on reopening).
46. **M-2** (`packages/ui/src/session/csp-sink.ts`, `createCspReportSink`, which both `/monitoring/csp` routes export as `POST`): only `application/reports+json` and `application/csp-report` (else 415, the body cancelled, no line); a token bucket per address, 30 a minute (else 429, no line), plus one process-wide bucket of 300 a minute that the brief did not ask for, so a sender rotating the `X-Forwarded-For` it claims still meets a ceiling; the address is the last `X-Forwarded-For` entry (`unknown` without one, #44); at most five violations a body; one line per (directive, blocked origin) a 60 s window; both maps hold at most 1000 keys (the oldest goes); the 64 kB cap stays. The apps have no Vitest, so "the route test" is the census check `the /monitoring/csp sink` in both apps' `census-errors.spec.ts` (`text/plain`, urlencoded and `application/json` 415; both report types 204; `ar` only, from an address of its own), and the unit tests drive `createCspReportSink` itself.
47. **L-1**: `/sign-in?reason=ended` clears the cookies only when `Sec-Fetch-Site` is `same-origin`, `same-site`, `none` or absent; a cross-site link renders the notice, clears nothing and does not redirect.
48. **L-2, deviation from the brief's "a relative `Location`"**: the proxy cannot return one on Next 16.4.3. The proxy adapter (`dist/server/web/adapter.js`) parses the proxy's `Location` with `new NextURL(location)`, whose `parseURL` is `new URL(String(url), base)` with no base, and `new NextURL('/sign-in')` throws `Invalid URL` (checked in Node). So the proxy builds the target on the configured public origin (`PUBLIC_WEB_URL` or `PUBLIC_ADMIN_URL`, required in staging and production, #6), never on `Host`. The adapter then rewrites a same-host target with `getRelativeURL`. The unit test runs that function over the proxy's answer: relative on the app's own host, the public origin (never the foreign host) otherwise. Against the built standalone servers the browser gets `Location: /sign-in?next=%2Forders&reason=ended` (web) and `/accounts` (admin, signed in on `/sign-in`) even with `Host`, `X-Forwarded-Host` or `Forwarded` set to `evil.example`.
49. **L-4**: `seedCensus` throws `censusSeedRefusal(config.app.env)` before it reads the credentials or opens a pool, so the guard holds for any caller, not only `census-main.ts` (#32).
50. **L-5**: HSTS is `max-age=63072000; includeSubDomains`, without `preload`: preloading is a one-way door (removal from the browsers' lists takes months) and needs the owner to submit the domain. `docs/architecture/web.md` §3.6 reads "(preload after the owner submits the domain)", and the root README says the same.
51. **L-6**: the installed Next 16.4.3's `dist/client/components/app-router-headers.js` defines two prefetch markers, `Next-Router-Prefetch` and `Next-Router-Segment-Prefetch` (both in `FLIGHT_HEADERS`; the router's `segment-cache` and `router-reducer` send no other). Its other headers (`RSC`, `Next-Router-State-Tree`, `Next-HMR-Refresh`, `Next-Url`, `Next-Action`) do not mark a prefetch. `isNavigation` refuses both markers, and also the browsers' `Sec-Purpose: prefetch` (speculation rules, `<link rel=prefetch>`) and the older `Purpose: prefetch`. A server action is a `POST` and was never a navigation.
