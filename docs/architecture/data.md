## 1. Principles

### 1.1 One database, three prefixes

- One PostgreSQL 16 database with PostGIS (ADR-0019), schema `public`. Tables carry the prefix of the context that owns them (ADR-0026, document 2 §1): `core_` (shared kernel), `del_` (Delivery), `wms_` (WMS). A fourth prefix, `rpt_`, is reserved for the read-only reporting objects of section 9.
- Foreign keys from `del_` and `wms_` to `core_` are allowed; none run between `del_` and `wms_`. Cross-context references are opaque UUID columns without a constraint (`del_orders.source_ref`, `del_order_items.wms_product_id`, `wms_packages.delivery_order_id`), as document 2 §1 requires.
- Business code never joins across prefixes. Cross-context reads go through ports (document 2 §1.1); cross-context reporting goes through `rpt_` views (section 9).

### 1.2 Where the schema lives

| Piece | Location | Rule |
|---|---|---|
| Table declarations | `apps/api/src/modules/<context>/schema/*.ts` (`kernel`, `delivery`, `wms`), one file per aggregate | private to the context, never re-exported from `public/`, so a cross-context join cannot compile without an import the architecture test rejects (ADR-0026) |
| Ledger declarations | `apps/api/src/modules/delivery/cash/ledger/schema.ts`, `apps/api/src/modules/wms/ledger/schema.ts` | importable only by the ledger service in the same folder (3.2) |
| Shared helpers | `packages/db` | column helpers (`id()`, `accountId()`, `timestamps()`, `version()`, `money()`), custom types (`geometry` Point, MultiPolygon, LineStringM; `xid8`), the unit of work that sets the tenancy context (4.2), the migrator wrapper, the tenancy schema test, trigger SQL templates, the seed runner |
| Migrations | `apps/api/drizzle/NNNN_<slug>.sql`, one ordered folder for the whole database | generated by `drizzle-kit generate` from the schema files, then reviewed and hand-edited where needed (section 11) |

Drizzle `relations()` are declared for typed reads only. There is no ORM-level cascade: every foreign key is `ON DELETE RESTRICT ON UPDATE RESTRICT`, and a service that removes rows deletes children explicitly. Aggregates are not deleted in normal operation; they reach a terminal, `archived` or `inactive` status (document 2 §2.3, §3.5).

### 1.3 Column conventions (every table unless the catalogue says otherwise)

| Column | Type | Rule |
|---|---|---|
| `id` | `uuid` primary key | UUIDv7 generated by the API (document 2 §8); SQL-side inserts (seeds, backfills) call `core_uuidv7()`, installed by the first migration; no database default |
| `account_id` | `uuid NOT NULL REFERENCES core_accounts` | on every operational table (ADR-0025); the leading column of tenant-facing indexes; exemptions in 2.4 |
| `created_at`, `updated_at` | `timestamptz NOT NULL DEFAULT now()` | `updated_at` is set by the repository base on every update; no trigger |
| `version` | `integer NOT NULL DEFAULT 1` | on Order and Assignment (D-22) and on every aggregate that publishes events, because the envelope `sequence` is that value (ADR-0027, document 2 §8); insert-only aggregates publish `sequence` 1 and carry no `version` |
| money | `bigint` halalas, plus one `currency char(3) NOT NULL DEFAULT 'SAR' CHECK (currency = 'SAR')` per row | no `numeric`, no floats (document 2 §8); `bigint` so report totals cannot overflow |
| enums | `text` with `CHECK (col IN (…))` | not PostgreSQL enum types: a CHECK can be widened and narrowed by expand and contract (section 11); Drizzle declares `text({ enum: [...] })` |
| bilingual text | `name_ar text NOT NULL`, `name_en text NOT NULL` | matches the contract fields (ADR-0016) |
| phones | `text CHECK (col ~ '^\+[1-9][0-9]{7,14}$')` | E.164, normalised before storage (document 4 §3.2) |
| business dates | `date` | Asia/Riyadh business day (cash day, slot day); every other time is `timestamptz` |
| human numbers | `number bigint`, unique per account | the display string (`D-000123`) is rendered by the API from the sequence format (section 7), never stored |
| geometry | `geometry(Point, 4326)` and friends | section 8 |
| JSON | `jsonb` | settings, envelopes, payloads, before and after images; never for a column that queries filter on often |

## 2. Table catalogue

Abbreviations: **AO** append-only (trigger, 3.1); **IO** insert-only, same trigger, corrections are new rows; **P** projection, rebuildable (3.5); **PU** partial unique index; `(a, b)` an index on those columns in that order. Every table has the 1.3 columns; only specific ones are listed. Every index on a tenant table leads with `account_id` unless marked **worker scan**: a cross-tenant partial index used only by worker jobs on the `elx_platform` role (4.4).

## 3. Ledgers and projections

### 3.1 Append-only triggers

Every table document 2 §8 names as append-only gets two triggers from the shared function below: a row trigger `BEFORE UPDATE OR DELETE` and a statement trigger `BEFORE TRUNCATE`, because row triggers do not fire on `TRUNCATE`. The `api-test` CI check includes, per table, a test that tries all three and expects SQLSTATE `EL001` (`platform.md` §4, handbook 02 "Schema change"). Join tables of insert-only aggregates get the same triggers as their parent.

| Table | Trigger | Blocks | Only lawful removal |
|---|---|---|---|
| `core_audit_log` | `core_reject_mutation` on the partitioned parent, inherited by partitions | update, delete, truncate | dropping a monthly partition older than 24 months (partition job, section 10) |
| `del_order_events` | `core_reject_mutation` | update, delete, truncate | per-account deletion tool (section 10) |
| `del_cod_collections` | `core_reject_mutation` | same | same |
| `del_cash_custody_entries` | `core_reject_mutation` | same | same |
| `del_driver_liability_entries` | `core_reject_mutation` | same | same |
| `del_cash_deposits`, `del_cash_deposit_collections` | `core_reject_mutation` | same | same |
| `wms_stock_movements` | `core_reject_mutation`, plus `wms_movement_validate` `BEFORE INSERT` | same | same |
| `core_outbox` | `core_outbox_envelope_immutable` `BEFORE UPDATE` | any change to an envelope column or `kind`; delivery-state columns stay writable (K-10) | delete by the pruning job (5.2) |
| `del_cash_reports` | `del_cash_report_closed` `BEFORE UPDATE OR DELETE`, `WHEN (OLD.status = 'closed')` | any change to a closed report (D-21) | per-account deletion tool |

```sql
CREATE FUNCTION core_reject_mutation() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  -- The per-account deletion tool (section 10) is the one exception.
  IF TG_OP = 'DELETE' AND current_user = 'elx_maintenance'
     AND current_setting('elx.purge_account', true) = OLD.account_id::text THEN
    RETURN OLD;
  END IF;
  RAISE EXCEPTION '% on % is forbidden: append-only', TG_OP, TG_TABLE_NAME
    USING ERRCODE = 'EL001';
END $$;

CREATE TRIGGER wms_stock_movements_append_only BEFORE UPDATE OR DELETE
  ON wms_stock_movements FOR EACH ROW EXECUTE FUNCTION core_reject_mutation();
CREATE TRIGGER wms_stock_movements_no_truncate BEFORE TRUNCATE
  ON wms_stock_movements FOR EACH STATEMENT EXECUTE FUNCTION core_reject_mutation();

CREATE FUNCTION core_outbox_envelope_immutable() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF (NEW.id, NEW.type, NEW.event_version, NEW.occurred_at, NEW.account_id,
      NEW.aggregate_type, NEW.aggregate_id, NEW.sequence, NEW.causation_id,
      NEW.correlation_id, NEW.payload, NEW.kind)
     IS DISTINCT FROM
     (OLD.id, OLD.type, OLD.event_version, OLD.occurred_at, OLD.account_id,
      OLD.aggregate_type, OLD.aggregate_id, OLD.sequence, OLD.causation_id,
      OLD.correlation_id, OLD.payload, OLD.kind) THEN
    RAISE EXCEPTION 'core_outbox envelope is immutable' USING ERRCODE = 'EL001';
  END IF;
  RETURN NEW;
END $$;
```

Disabling a trigger needs table ownership, which no runtime role has (3.2), and `session_replication_role` needs a superuser, which no application credential is. A migration that drops or replaces one of these triggers is called out in the PR's merge danger.

Design rule that keeps purging possible: append-only rows carry ids, amounts, codes and points, never names or phone numbers. Personal data lives in mutable rows (`del_orders`, `core_users`) where it can be redacted in place (section 10).

### 3.2 The ledger service is the only writer

Decision (proposed ADR-0031): application single writer, backed by database privileges and the trigger; no `SECURITY DEFINER` functions.

- **Module boundary.** The Drizzle objects for `wms_stock_movements`, `wms_stock_levels`, `wms_stock_summaries`, `del_cod_collections`, `del_cash_custody_entries`, `del_driver_liability_entries`, `del_cash_deposits`, `del_driver_cash_positions` and the ledger join tables live in the ledger folders (1.2). The ADR-0026 architecture test rejects an import of those files from anywhere else, so no query-builder write to a ledger can exist outside the ledger services (AGENTS.md hard rule, ADR-0020).
- **Privileges.** The runtime roles `elx_app` and `elx_platform` hold `SELECT, INSERT` on ledger tables and nothing more; `UPDATE`, `DELETE` and `TRUNCATE` are not granted. Neither role owns a table; `elx_owner` does and is used only by the migration and partition jobs. `elx_maintenance` holds `DELETE` for the deletion tool and is in no API or worker pool. Roles in 4.4.
- **Trigger.** The third line, for anything that reaches the table through a role with more rights.

Why not `SECURITY DEFINER` functions: they would keep the caller's transaction, but the W-6 check under the StockLevel row lock, the D-20 arithmetic and the projection upserts would move into PL/pgSQL, outside the TypeScript types, the unit tests and the reviewers' habits. Any code holding the runtime role could still call the function, so it restricts callers no more than the module boundary does. A separate database role per ledger service would need a second connection, which breaks the single transaction that W-9 (pick and release together) and D-20 (custody and liability together) require.

### 3.3 The `ledger_seq` cursor (StockSummary)

StockLevel is maintained inside the movement's transaction under its row lock (document 2 §4.5, W-6, W-7); `del_driver_cash_positions` is maintained the same way by the cash ledger service. Only StockSummary trails, through a cursor.

The problem: `ledger_seq` is allocated at insert while transactions commit in any order, so a reader that has passed seq 101 can miss seq 100 committed a moment later. Document 2 §4.5 requires reading only rows below the oldest in-flight transaction.

Mechanism, chosen here as the implementation of document 2 §4.5 and ADR-0011 (no new decision): every movement records `tx_id xid8 DEFAULT pg_current_xact_id()`. Every transaction with an id below `pg_snapshot_xmin(pg_current_snapshot())` has finished, so its rows are final and visible. The cursor is the pair `(tx_id, ledger_seq)` in `wms_projection_cursors`, compared as a row value:

```sql
SELECT tx_id, ledger_seq, account_id, product_id
FROM wms_stock_movements
WHERE (tx_id, ledger_seq) > ($1::xid8, $2::bigint)
  AND tx_id < pg_snapshot_xmin(pg_current_snapshot())
ORDER BY tx_id, ledger_seq
LIMIT 5000;
```

The batch is read in cursor order and grouped in code, never grouped in SQL before the `LIMIT`, so the cursor can only move to a row that was actually read. For each distinct `(account, product)` in the batch the projector recomputes the summary absolutely: `on_hand` as the sum of `wms_stock_levels` over the product's non-system locations, `reserved` as the sum of open `wms_reservations`. It bumps `version`, sets `as_of_ledger_seq`, supersedes and inserts the channel publication, writes the `wms.stock.available_changed` outbox row (document 2 §5.3) and advances the cursor to the last row of the batch, all in one transaction. Recomputing instead of adding deltas makes a reprocessed batch harmless and a rebuild trivial. Allocation (W-8) reads `available` under `FOR UPDATE` on the summary row and increments `reserved` itself, so the guard holds between projector runs. The projector runs on the worker every 2 seconds, single leader by the Redis lock `elx:lock:stock-projector`.

Rejected alternative: an advisory lock serialising every ledger write so that `ledger_seq` order equals commit order. Simpler to read, but it couples all WMS write throughput to one lock. Known costs of the chosen mechanism: a long write transaction holds `xmin` back and delays summaries (alert on cursor lag above 60 s); a logical dump and restore into a new cluster (not a physical restore or point-in-time recovery) restarts transaction ids, so the runbook resets the cursor and runs the rebuild (3.5) after every logical restore, including the weekly staging refresh.

### 3.4 Nightly assertions

Run at 03:00 Asia/Riyadh by the worker on `elx_platform`, results written to the ops log and exported as the "ledger assertion drift" metric (`platform.md` §7); any non-empty result opens an alert (W-7). The same queries run in CI (`apps/api/test/ledger/`, handbook 03) and in the diagnose console.

Stock (ADR-0011):

1. StockLevel equals the ledger: for every non-system `(location, product, lot, serial)`, inflow minus outflow equals `on_hand`, and no ledger balance lacks a StockLevel row.
2. StockSummary equals the sum of StockLevel and the open reservations for every product.
3. No serial has positive balance in two locations; no lot or serial column disagrees with the product mode (W-4).
4. Every open reservation belongs to a non-terminal fulfilment order line (W-8).

```sql
-- Assertion 1 for one account; every returned row is drift
WITH ledger AS (
  SELECT m.account_id, m.location_id, m.product_id, m.lot_id, m.serial_id, sum(m.q) AS qty
  FROM (SELECT account_id, to_location_id AS location_id, product_id, lot_id, serial_id, quantity AS q
          FROM wms_stock_movements WHERE account_id = $1
        UNION ALL
        SELECT account_id, from_location_id, product_id, lot_id, serial_id, -quantity
          FROM wms_stock_movements WHERE account_id = $1) m
  JOIN wms_locations l ON l.id = m.location_id AND l.type <> 'system'
  GROUP BY 1, 2, 3, 4, 5)
SELECT * FROM ledger
FULL JOIN (SELECT * FROM wms_stock_levels WHERE account_id = $1) s
  USING (account_id, location_id, product_id, lot_id, serial_id)
WHERE coalesce(ledger.qty, 0) <> coalesce(s.on_hand, 0);
```

(`USING` treats NULL lot and serial as unequal; the real query compares them with `IS NOT DISTINCT FROM`.)

Cash (ADR-0007):

1. Every cash collection has a first custody entry `collected`; every card, mada and wallet collection has exactly one entry, `not_held` (D-18).
2. `del_driver_cash_positions.cash_in_hand` equals the sum of the driver's cash collections whose latest custody is `collected`; `liability_balance` equals the sum of the driver's liability entries (D-20).
3. For every confirmed handover, `counted − expected` equals the liability entry for that handover (zero means none exists).
4. Every delivered order with `cod_amount > 0` has collections summing exactly to `cod_amount` (D-7).
5. Every closed cash report equals the recomputation from the collections and custody entries of its site and date (D-21).

### 3.5 Rebuild procedure

Projections can be dropped and rebuilt from the ledger at any time (document 2 §4.5). Per account, by the platform runbook "rebuild projections":

1. Take `pg_advisory_lock(hashtextextended('wms_ledger:' || account_id, 0))`. The ledger service takes the same key with `pg_advisory_xact_lock_shared` in every movement transaction, so writes never wait for each other but do wait for a rebuild.
2. In one transaction: delete the account's `wms_stock_levels` rows and reinsert them from the ledger (assertion 1 as an `INSERT … SELECT`); recompute `wms_stock_summaries` from the new levels and open reservations.
3. Run stock assertions 1 to 3 for the account; commit only if all are empty.
4. Cash: the same pattern for `del_driver_cash_positions` under the key `del_cash_ledger:<account_id>`.
5. Release the lock and write an audit row (`action = projections.rebuilt`).

A full rebuild loops over accounts. Nothing depends on the global cursor, which simply continues.

## 4. Tenancy enforcement

### 4.1 Schema test

Part of `api-test` (`platform.md` §4), reading `pg_catalog` after migrations run from zero. It fails when:

- a `core_`, `del_`, `wms_` or `rpt_` table not in the exemption list (2.4) lacks `account_id uuid NOT NULL` with a foreign key to `core_accounts`, or lacks an index whose first column is `account_id`;
- a unique index on such a table omits `account_id`, unless it is on a globally unique value listed in the test (ids, token hashes, `ledger_seq`, `(consumer, event_id)`, worker-owned keys such as `(driver_id, slot)`). Uniqueness is checked across tenants even under RLS, so a per-tenant key without `account_id` would leak existence;
- an operational table has no `tenant_isolation` policy (4.3), from wave 0, before RLS is enabled;
- an append-only table (3.1) lacks its triggers;
- a column comment carries a `pii:` tag that the staging anonymiser does not cover, or an inventory column (section 10) lacks the tag.

### 4.2 Repository base and unit of work

- The guard resolves the request context once into `AsyncLocalStorage` (document 4 §5). Every request that touches the database runs inside one transaction opened by the unit of work in `packages/db`, whose first statement is `SELECT set_config('elx.account_id', $1, true)`. The `true` makes the setting transaction-local, so a pooled connection never carries one request's account into the next.
- The repository base adds `eq(table.accountId, ctx.accountId)` to every select, update and delete and sets `account_id` from the context on every insert. Omitting the predicate needs `unscoped()`, which exists only on platform repositories (4.4); a lint rule flags it elsewhere.
- No handler, DTO or contract carries `account_id` as input (K-3, contracts §1).

### 4.3 RLS policy template

```sql
CREATE POLICY tenant_isolation ON del_orders TO elx_app
  USING (account_id = NULLIF(current_setting('elx.account_id', true), '')::uuid)
  WITH CHECK (account_id = NULLIF(current_setting('elx.account_id', true), '')::uuid);
CREATE POLICY platform_access ON del_orders TO elx_platform USING (true) WITH CHECK (true);
-- At the end of wave 1 only, one migration for every operational table:
ALTER TABLE del_orders ENABLE ROW LEVEL SECURITY;
```

`NULLIF` matters: once a transaction-local setting has been used on a connection, later reads of it return an empty string, not NULL. Casting `''` would raise an error; NULL matches no row. A missing context therefore reads nothing and writes nothing.

### 4.4 Roles, the platform cross-tenant path and background jobs (proposed ADR-0031)

| Role | Used by | Rights |
|---|---|---|
| `elx_owner` | migration job, partition job | owns every object; never in an API or worker pool |
| `elx_app` | API and worker pools for tenant work | DML on operational tables, `SELECT, INSERT` on ledgers, subject to `tenant_isolation` |
| `elx_platform` | a separate pool for `@CrossTenant()` platform handlers (document 4 §5) and cross-tenant worker jobs: outbox relay, projectors, offer expiry, retention, assertions | the same grants as `elx_app`; the `platform_access` policy shows it every account |
| `elx_maintenance` | the per-account export and deletion tool only (section 10) | `SELECT` everywhere and `DELETE` everywhere, ledgers included; the trigger honours a ledger delete only with `elx.purge_account` set to that row's account |

- The `elx_platform` pool is constructed only in the platform module and the worker's system jobs; the architecture test rejects its import elsewhere. Every platform handler call still writes the audit row with the target account (document 4 §5).
- Background jobs carry `account_id` in the payload (document 4 §5). The job runner opens the unit of work with that account before the handler runs; a tenant job handler cannot reach the `elx_platform` pool. A job without an account context runs on `elx_platform` and may touch only platform tables and the worker scans marked in section 2.

### 4.5 What breaks if RLS is enabled before the end of wave 1

Document 4 §5 defers RLS until the schema is stable. Enabled earlier:

- Default deny is silent. A table that ships without its policy returns zero rows instead of an error, and tests seeded through the same role pass on empty results.
- Work that runs outside the unit of work (an autocommit read in a health check, a script, an early worker) loses its rows without failing.
- Cross-tenant worker jobs need the `elx_platform` pool first; without it the relay and the projector stall.
- Every expand migration must also add policies, which slows the schema churn of waves 0 and 1 for no isolation the repository predicate does not already give.

Plan: policies are created with every table from wave 0 (the schema test requires them) while RLS stays disabled; the integration suite runs one extra lane with RLS enabled from the first table, so the failure modes above surface in CI; at wave 1 exit one migration enables RLS on every operational table, and the schema test then also asserts `relrowsecurity`.

## 5. Idempotency and outbox storage

### 5.1 `core_idempotency_keys`

- Reserve: insert `(account_id, principal_id, key, request_hash, state = 'in_progress')` in the business transaction, before the write (K-8). A unique violation means a replay: same hash and `completed` returns the stored response; same hash and `in_progress` returns `409` with `Retry-After` (the original is still running); a different hash returns `422 idempotency_key_reused`.
- Complete: the same transaction stores `response_status` and `response_body` and sets `expires_at = created_at + 24 h`.
- Purge: an hourly worker job deletes rows with `expires_at < now()` in batches of 10,000 by the worker-scan index (K-9). Driver replays older than 24 hours are answered from `del_order_events` through the D-15 unique key.

### 5.2 `core_outbox`

- Relay: single leader by the Redis lock `elx:lock:outbox-relay` (TTL 30 s, renewed every 10 s; `platform.md` §5). Each tick selects `status = 'pending' AND next_attempt_at <= now()` for accounts that are not suspended, `ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED`, enqueues to BullMQ by kind with the outbox `id` as job id (BullMQ ignores a duplicate job id) and sets `status = 'enqueued'`. `SKIP LOCKED` protects against two leaders after a lost lock. A suspended account's rows of every kind except `internal_event` stay `pending` (K-2); internal events still flow so the suspension's own consumers run.
- Stuck rows: a sweeper returns rows `enqueued` for more than 10 minutes to `pending` (Redis lost the job); the job-id dedupe makes a double enqueue harmless.
- Supersede: a new row with a `supersede_key` marks the pending row with the same key `superseded` in the same transaction; the partial unique index allows one pending row per key.
- Pruning, not partitioning, until the trigger in section 12: a daily job deletes `done` and `superseded` rows older than 7 days and `dead` rows older than 30 days, in batches of 5,000. Seven days keeps recent effects inspectable in the platform admin.
- Dead letters: a worker sets `dead` after the kind's retry budget; the platform admin lists and replays them (`/v1/platform/outbox`). Replay refuses rows older than the consumer-receipt window (5.3).

```sql
-- Oldest due pending row (alert above 5 minutes, platform.md §7)
SELECT now() - min(next_attempt_at) FROM core_outbox
WHERE status = 'pending' AND next_attempt_at <= now();
-- Dead rows per account and kind
SELECT account_id, kind, count(*), min(created_at) FROM core_outbox
WHERE status = 'dead' GROUP BY account_id, kind;
```

### 5.3 Consumer receipts and parked events

- `core_consumer_receipts` rows are written in the consumer's transaction (document 2 §2.7) and purged after 35 days, longer than the 30-day dead-row window, so any replayable event still finds its receipt.
- Parked events (a `sequence` gap, document 2 §6.2) are BullMQ delayed jobs, not rows. After 15 minutes parked, the event moves to `core_consumer_dead_letters`, which feeds the platform `ConsumerList` (`parked`, `dead`). Dead letters are kept 30 days.
- Merchant webhooks: one `core_webhook_deliveries` row per subscription and event, created by the webhook fan-out consumer and kept 30 days as the merchant-visible delivery log (ADR-0040).

## 6. Telemetry storage (ADR-0028, document 2 §7)

- Ring: one `INSERT … ON CONFLICT (driver_id, slot) DO UPDATE` per accepted point, with `seq` taken from `del_driver_location_heads` (one `UPDATE … SET last_seq = last_seq + n RETURNING last_seq` per batch) and `slot = seq % 240`. The table holds at most drivers × 240 rows. It is update-heavy, so it gets `fillfactor = 70` for heap-only updates and aggressive per-table autovacuum (`autovacuum_vacuum_scale_factor = 0.02`).
- Head: `del_driver_location_heads` also keeps the latest point (the fallback for dispatcher maps when the Redis key has expired) and `trail_seq` for the trail appender.
- Trail: every 5 minutes a single-leader worker job (`elx:lock:trail-appender`) reads, per driver, ring rows with `seq > trail_seq`, simplifies only the new segment (`ST_Simplify`, about 5 m tolerance), appends it to the day's `del_driver_trails` row with `ST_MakeLine` (M = Unix seconds, so dispute review can ask where the driver was at a given time) and advances `trail_seq` in the same transaction. The appender must run more often than the ring wraps (one hour at 15 s).
- Retention: a daily job deletes trails with `business_date < current_date - 90` (document 2 §9 question 5 may lengthen this) and the ring and head rows of archived drivers.

| Redis key | Type | TTL | Purpose |
|---|---|---|---|
| `elx:loc:latest:{account_id}:{driver_id}` | hash: point, client_ts, server_ts, shift status | 600 s | latest position for maps and polling (contracts §6) |
| `elx:loc:{account_id}` | pub/sub channel | none | fan-out to SSE streams (dispatch board; recipient pages filtered to their driver) |
| `elx:sse:{account_id}` | stream trimmed by `MINID` to 15 minutes | rolling | `Last-Event-ID` replay buffer (contracts §6, ADR-0029) |
| `elx:lock:outbox-relay`, `elx:lock:stock-projector`, `elx:lock:trail-appender` | string | 30 s, renewed | single-leader locks |

Redis is never the source of truth (`platform.md` §2): losing it costs the live fan-out and the replay buffer until the next ping or event.

## 7. Sequences

- Allocation inside the business transaction (document 2 §8, D-2): `UPDATE core_sequences SET next_value = next_value + $n WHERE account_id = $1 AND name = $2 RETURNING next_value - $n`. The row lock is held until commit and a rollback restores the value, so numbers are gap-free and monotonic. Creators of one kind in one account serialise on that row, which at 500 orders a day is invisible; a CSV import allocates a block once per batch with `$n` above 1.
- Rows for every name are created at provisioning (K-1), so allocation never inserts.
- The display format is fixed in code and applied at render; the stored `number` is the integer. Filtering by a display number parses the prefix and queries `(account_id, number)`.

| `name` | Owner table | Display | Example |
|---|---|---|---|
| `delivery_order` | `del_orders` | `D-` and six digits, wider when needed | `D-000123` |
| `purchase_order` | `wms_purchase_orders` | `PO-` and six digits | `PO-000045` |
| `inbound_receipt` | `wms_inbound_receipts` | `GR-` and six digits | `GR-000310` |
| `fulfilment_order` | `wms_fulfilment_orders` | `F-` and six digits | `F-004512` |

## 8. Geo (ADR-0019, ADR-0010)

- PostGIS `geometry` with SRID 4326 for every spatial column: site points, order address points, event and attempt points, ring points, zone boundaries (MultiPolygon), trails (LineStringM). Contracts carry `{lat, lng}`; the API converts with `ST_SetSRID(ST_MakePoint(lng, lat), 4326)` and the Drizzle custom type keeps longitude first.
- GiST indexes on `core_sites.point`, `del_orders.address_point`, `del_zones.boundary` and `del_driver_trails.path` (document 2 §8).
- Distances in metres cast to geography (`ST_DWithin(a::geography, b::geography, 500)`); planar degrees are never used as a distance.
- Coverage (D-3): `SELECT z.id FROM del_zones z JOIN del_coverage c ON c.zone_id = z.id AND c.site_id = $2 WHERE z.account_id = $1 AND z.active AND ST_Covers(z.boundary, $3)`. `ST_Covers` rather than `ST_Contains`, so a point on a boundary counts as covered. The same query serves `CoverageQuery` (document 2 §1.1) and `/coverage/check`.
- Zone boundaries are validated on write (`ST_IsValid`) and stored as given; official boundaries are imported by a seed script per city.
- Distance matrix cache (ADR-0010): `del_distance_matrix_cache` holds one row per site, business date, provider and hash of the ordered point list, with the n × n durations and distances. A solve reads the cache by hash before calling Hudhud; rows older than 7 days are deleted daily. A pairwise-cell cache that survives adding one stop is left to the wave 2 routing order, if Hudhud cost demands it.

## 9. Reporting

Dashboards need joins across contexts (an order with its package, a site's deliveries beside its cash). ADR-0026 allows these only as read-only views defined here.

| Object | Spans | Serves | Kind |
|---|---|---|---|
| `rpt_order_fulfilment` | `del_orders` left join `wms_packages` on `delivery_order_id`, left join `wms_fulfilment_orders` | order-to-package trace, WMS pilot dashboards | plain view |
| `rpt_site_day` | orders by status, attempts, COD by method, deposits, per site and business date | owner dashboard "today" | plain view |
| `rpt_driver_day` | orders delivered and attempted, cash held, liability, shift hours, per driver and date | driver performance, pay checks | plain view |
| `rpt_stock_position` | `wms_stock_summaries` with open fulfilment demand and pending channel publications | stock screen | plain view |
| `rpt_daily_kpis` | the views above, per account and business date, closed days only | trends, monthly reports | table, filled nightly |

- Plain views are created `WITH (security_invoker = true)` so the reader's RLS policies apply (section 4), owned by `elx_owner`, granted `SELECT` to the runtime roles, and read only by a `reporting` module (`apps/api/src/modules/reporting/`) that imports no context schema and writes nothing.
- No materialised views: PostgreSQL does not apply RLS to them, so a tenant could read another tenant's aggregate through one. History is a real table, `rpt_daily_kpis`, with `account_id`, its index and the tenancy policy, filled at 02:00 Asia/Riyadh for the previous day and recomputable for any range; "today" figures always come from the live views.
- `rpt_daily_kpis` is the only table with the `rpt_` prefix, and only the reporting job writes it.

## 10. Personal data inventory and retention

Every column below carries `COMMENT ON COLUMN … IS 'pii:<actor>'`; the schema test (4.1) keeps the comments, this list and the staging anonymiser in step. A PR that adds a personal-data column updates all three.

| Actor | Columns | Retention |
|---|---|---|
| Recipient | `del_orders.recipient_name`, `recipient_phone`, `recipient_alt_phone`, `address_text`, `address_district`, `national_address_short_code`, `address_point`; the recipient and address snapshot on `wms_fulfilment_orders`; `del_order_events.point`, `del_attempts.point`, `del_attempts.note` | life of the account (the merchant's records); open question 1 |
| Recipient | proof files behind `del_proofs.storage_key` (photos, signatures, ID checks) | two years after the order's `terminal_at` by default, per account policy (`platform.md` §6); the job deletes the object, sets `purged_at` and writes an audit row |
| Recipient | `core_inbound_webhooks.payload` (channel orders carry name, phone, address); `core_outbox.payload` of `message` rows | inbound 30 days; outbox per 5.2 (7 days done, 30 days dead) |
| Recipient | `del_tracking_tokens` rows | `track` until the order closes plus 30 days; `reschedule` and `address_pin` 48 hours (document 4 §3.5); deleted daily after expiry |
| Driver | `core_users.name`, `phone`; `del_drivers.cash_pin_hash`; `del_driver_devices.device_id`, `push_token` | life of the membership; the push token is cleared on archive |
| Driver | `del_driver_locations`, `del_driver_location_heads` | ring overwritten within one hour; deleted when the driver is archived |

| Any actor | `core_otp_challenges.phone`, `ip` | deleted 1 hour after `expires_at` (OTP lifetime 5 minutes) |
| Any actor | `core_refresh_tokens`, `core_invitations`, `core_password_resets`, `core_auth_challenges` (`pending_phone`, `ip`) | deleted 7 days after expiry or use |
| Supplier contact | `wms_suppliers.contact` | life of the account |

Rules:

- OTP codes are never stored readable: `core_otp_challenges.code_hash` is a hash, and the WhatsApp `message` outbox row that sends the code carries it encrypted with the credentials key and is deleted 1 hour after `done`, not after 7 days.
- Secrets that are only verified are hashed, not encrypted: passwords and cash PINs (Argon2id), API keys and refresh, invitation, reset and verification tokens (SHA-256).
- Encrypted at rest with a key from the secret store and a key-id column (`platform.md` §3): `core_channel_connections.credentials_ciphertext` and `webhook_secret_ciphertext`, `core_webhook_subscriptions.secret_ciphertext` and `previous_secret_ciphertext`, `core_platform_staff.totp_secret_ciphertext`. AES-256-GCM in the API, nonce stored with the ciphertext. Rotation adds a key, a worker job re-encrypts rows by `*_key_id`, then the old key is retired, so no stored credential is unreadable mid-rotation.
- Per-account export: a platform admin tool (`platform.md` §6) on `elx_maintenance` writes one archive per account (CSV per table plus proof files) to the bucket and returns a signed URL valid 24 hours; audit rows on request and download.
- Per-account deletion: only for a `closed` account, after its export (open question 2 for the waiting period). The tool sets `elx.purge_account`, deletes the account's rows table by table, children first, ledgers included (3.1), then its object-storage prefixes. The audit rows of the deletion itself are kept, with ids and no personal data.
- A single recipient's erasure request is served by redacting the mutable recipient columns of that recipient's orders in place; ledger rows hold no names (3.1).
- Backups (`platform.md` §6) expire after 35 days, so a deletion is complete everywhere within 35 days.

## 11. Migration workflow

1. **Change the schema file** in the owning context (1.2) and run `drizzle-kit generate`; the SQL lands in `apps/api/drizzle/`.
2. **Hand-edit and review the SQL.** By hand: triggers, RLS policies, PostGIS types and GiST indexes, generated columns, partial and `NULLS NOT DISTINCT` indexes, CHECKs that call functions, the `pii:` comments, and `CREATE INDEX CONCURRENTLY` on large tables (its own migration, outside a transaction). The SQL is reviewed as code (ADR-0020, handbook 02 "Schema change").
3. **Expand and contract** (`platform.md` §5). A PR may add tables, nullable columns, columns with defaults, indexes, widened CHECKs and backfills. A rename goes add, dual write, backfill, switch reads, drop. A destructive step (drop, rename, type narrowing, CHECK narrowing, `NOT NULL` on an existing column) ships in a later PR, after the code that stopped needing the old shape is in production, with its backfill plan in the PR. Every migration PR states merge danger one-way door.
4. **Large backfills** run as batched worker jobs (10,000 rows per transaction, resumable by id), not inside the migration, so the migration job stays short.
5. **One-shot migration job**: `api --role migrate` runs as `elx_owner` before the new API starts, takes the migrator's advisory lock so two deploys cannot race, applies pending files, ensures the next three monthly `core_audit_log` partitions exist, and exits. `/ready` stays not ready until the database is at the expected version.
6. **Seeds and fixtures**: `packages/db/seed/` holds deterministic fixtures with fixed UUIDv7 ids: two accounts (the tenancy tests need a second tenant that must stay invisible), sites of every kind, Riyadh and Jeddah zones with real boundaries, drivers and vehicles, orders in every state of §3.13, COD in every custody state, and a stocked warehouse with lot and serial products. `ci` migrates from zero and seeds on every run (`platform.md` §4).
7. **Isolated stacks**: the development database is never migrated by an executor (`platform.md` §1). A stack (`stack-a`, `stack-b`) gets a clone, `CREATE DATABASE elx_stack_a TEMPLATE elx_seed`, where `elx_seed` is built once from zero plus seeds; the branch's migrations then run against the clone only (handbook 03). Clones are dropped when the stack stops.
8. **Staging** receives the weekly anonymised copy (`platform.md` §1): the anonymiser rewrites every `pii:` column, then the projection rebuild runs (3.3).
9. **Parallel orders** (A-27, CHORE-3). New migrations are timestamp-named, `YYYYMMDDHHmmss_<slug>.sql` with a matching `meta/<YYYYMMDDHHmmss>_snapshot.json` (`apps/api/drizzle.config.ts` `migrations.prefix: 'timestamp'`); `0000` to `0015` keep their index names and stay byte-identical. The runner (`packages/db/src/migrate.ts`) applies every journal entry it has not recorded, in journal order and never by file name, in one transaction, keeping Drizzle's bookkeeping (`drizzle.__drizzle_migrations`: SHA-256 of the file, `created_at` = the journal `when`). An unapplied entry older than the last applied one (a parallel order generated it earlier but merged later) is applied with one log line, `migration <tag> is older than the last applied one; applying in journal order`; Drizzle's own `migrate()` would skip it silently, so the runner does not use it. It refuses an applied file that was edited or removed, and two journal entries with the same `when`.
   - **Journal merge.** Two orders that each add a migration both append to `meta/_journal.json`, so the second merge conflicts there. Keep both entries, ordered by `when`, renumber `idx` to be consecutive from 0, and run `migrate` twice on a scratch database (it applies, then reports nothing to migrate). No git merge driver: a union merge breaks the JSON.
   - **Forked snapshot chain.** Each order's snapshot names the same parent (`prevId`), and its contents lack the other order's schema. drizzle-kit 0.31 then refuses to generate at all ("… are pointing to a parent snapshot … which is a collision"). After rebasing, the order that merges second repairs the chain before its PR merges: (1) set the `prevId` of its first own snapshot to the `id` of main's newest snapshot; (2) run `drizzle-kit generate` once; if it writes nothing, stop; if it writes a migration that only repeats what main already holds (the other order's tables, which its snapshot lacked), delete that SQL file and its journal entry and keep the snapshot it wrote, which is the merged schema and the chain's new head; anything beyond a repeat is a real divergence to review as a migration; (3) a second `generate` must report no changes, and `migrate.test.ts` on a fresh database plus the tenancy schema test must pass. An own migration without hand edits may instead be regenerated: delete its SQL file, snapshot and journal entry, then `generate` again (new timestamp, linear chain).

## 12. Capacity and growth

Assumptions per order at the first-customer profile (foundation plan §1: 50 to 500 orders a day, 3 to 15 drivers, COD on at least half): 2 items, 8 order events, 1.3 offers, 1.1 assignments, 1.1 attempts, 1.5 proofs, 0.5 COD collections, 1.5 custody entries, 10 outbox rows, 4 audit rows, 10 idempotency keys; with WMS, 6 movements. Pings every 15 s during 10-hour shifts.

| Table | One merchant at 500 orders a day, 15 drivers | 100 such merchants |
|---|---|---|
| `del_orders` | 500 a day; 180 k a year | 50 k a day; 18 M a year |
| `del_order_events` | 4 k a day; 1.5 M a year | 400 k a day; 146 M a year |
| `wms_stock_movements` | 3 k a day; 1.1 M a year | 300 k a day; 110 M a year |
| `del_proofs` (rows; files in storage) | 750 a day; 550 k live over two years | 75 k a day; 55 M live |
| `core_outbox` (live after pruning) | 35 k | 3.5 M |
| `core_idempotency_keys` (live, 24 h) | 5 k | 500 k |
| `core_audit_log` | 2 k a day; 1.5 M over two years | 200 k a day; 146 M over two years |
| `del_driver_locations` (ring) | 3,600 rows, fixed | 360 k rows, fixed |
| `del_driver_trails` | 1,350 rows live, about 40 MB | 135 k rows live, about 4 GB |

At one merchant every table is small; nothing is partitioned except `core_audit_log`, whose monthly partitions exist for retention, not size.

Partitioning trigger, any one of: a table above 50 GB or 200 M rows; its autovacuum taking more than an hour; p95 of its hottest indexed query above 50 ms after index tuning. Expected order at 100 merchants:

| Table | When | How |
|---|---|---|
| `del_order_events` | year two | hash by `account_id` (16 partitions), which keeps `(account_id, idempotency_key)` unique forever (D-15); a time partition could not |
| `wms_stock_movements` | year two | hash by `account_id`; `ledger_seq` and the `(tx_id, ledger_seq)` cursor are unaffected |
| `del_proofs` | year two | range by `created_at`, yearly, which also simplifies the two-year purge |
| `core_outbox` | when inserts pass 2 M a day | range by `created_at`, daily; a partition is dropped once it holds no `pending`, `enqueued` or `dead` rows |
| `core_audit_log` | from day one | range by month, as above |

Converting a live table to partitions is its own expand and contract sequence: new partitioned table, dual write from the repository, batched copy, switch reads, drop the old table in a later PR. Each conversion gets its own order.

## 13. Open questions for the owner

1. **Recipient data on orders.** Proposed: recipient names, phones and addresses stay for the life of the merchant's account, because the merchant needs them for returns and disputes. Alternative: redact them 24 months after an order closes, in step with proof deletion. Which?
2. **Closed accounts.** Proposed: a closed account's data is kept 90 days with export available, then deleted by the deletion tool. Is 90 days right, and may a merchant ask for immediate deletion?
3. **Merchant webhook log.** Proposed: delivery attempts stay visible to merchants for 30 days. Enough?
4. **Database provider conditions.** The design needs four database roles, PostGIS, `citext`, and the right to create triggers and policies without a superuser. Please make these a condition when choosing the provider (`platform.md` §10, decision 1).
