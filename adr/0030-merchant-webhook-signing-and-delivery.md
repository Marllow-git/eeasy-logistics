# ADR-0030: Sign merchant webhooks with a timestamped HMAC and verify each subscription by token

- **Status:** proposed
- **Date:** 2026-10-31
- **Deciders:** architecture lead, owner to accept
- **Source:** API contracts (document 3) `webhooks.md`; foundation plan §9 (Bolesa store webhooks, Logestechs gap); ADR-0024, ADR-0027

## Context

Wave 4 exposes domain events to merchants as webhooks. The Logestechs census (`docs/references/logestechs/public-api.md`) found a static password header, no signature and no retries; OTO signs a few fields, not the body. A merchant's receiver must be able to prove a request came from us, reject a replayed capture, survive our retries and get events for one order in order. A subscription URL typed by a merchant can also point at a host the merchant does not control.

## Decision

Each subscription has its own 32-byte secret, generated by us, shown once and stored encrypted. Every delivery carries `X-Eeasy-Timestamp` (Unix seconds) and `X-Eeasy-Signature: v1=<hex HMAC-SHA256(secret, "<timestamp>.<raw body>")>`; receivers reject timestamps more than 5 minutes off and deduplicate on the envelope `id`. Rotation issues a new secret and signs with both for 24 hours. Delivery is at least once from the outbox (ADR-0024): one in-flight delivery per subscription and aggregate in `sequence` order, a 10-second timeout, exponential backoff for up to 24 hours, then `dead`, listed in the merchant web app and redeliverable. A new or re-pointed subscription stays `pending_verification` until the integrator returns the one-time token we sent to the URL; the token is stored only as a hash. URLs must be `https` on port 443. The API checks only syntax and address class at creation; reachability and the verification request run through the outbox. Each delivery resolves the host once, refuses private, loopback, link-local, `0.0.0.0/8`, `100.64.0.0/10`, `198.18.0.0/15`, multicast and IPv4-mapped IPv6 addresses, connects to the checked address and follows no redirect. The delivery log exposes the status code and a fixed error class, never the response body. Subscription creation and URL changes are limited to 5 per hour per account.

## Consequences

Receivers verify with a few lines in any language; the signature covers the whole body and the time. The relay needs per-aggregate queues per subscription and a dead-letter view. We must document a verification snippet and keep the sample payloads page current with the catalogue.

## Alternatives considered

Signing selected fields (OTO): a body change can pass verification. Static shared header (Logestechs): no integrity, replayable forever. Mutual TLS: strong but too heavy for most Saudi merchant stacks. Synchronous challenge echo at creation: fails for receivers behind queues; the asynchronous token works for both.
