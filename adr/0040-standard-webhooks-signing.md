# ADR-0040: Sign merchant webhooks with the Standard Webhooks specification

- **Status:** accepted
- **Date:** 2026-11-01
- **Deciders:** owner
- **Source:** owner ruling 2026-11-01 (Q-43); `docs/research/webhook-signing-standards-2026-11.md`; `docs/research/backend-library-census-2026-11.md` §6; supersedes ADR-0030

## Context

ADR-0030 (proposed, nothing built) signs merchant webhooks with our own headers, `X-Eeasy-Timestamp` and `X-Eeasy-Signature: v1=<hex HMAC-SHA256("<timestamp>.<body>")>`. The Standard Webhooks specification (v1, Apache-2.0) does the same thing: HMAC-SHA256 with a 5-minute tolerance and two signatures during a rotation. Its differences are a fixed format (`webhook-id`, `webhook-timestamp`, `webhook-signature`, `whsec_` secrets, base64), the message id inside the signed string, and an optional Ed25519 scheme (`v1a`). The project publishes verification libraries for the languages our merchants use (PHP, Python, Node, .NET, Go, Java, Ruby and others). OpenAI and Supabase state they use it. Stripe signs `timestamp.payload` the same way under its own names; GitHub, Shopify and Twilio sign no timestamp. Merchants will verify our webhooks in Laravel, Node, .NET and Python stacks.

## Decision

This ADR replaces ADR-0030 in full. Its delivery and subscription rules are restated unchanged unless marked new.

1. **Signing: Standard Webhooks v1, symmetric.**
   - Every delivery carries `webhook-id` (the envelope `id`, the same on every retry), `webhook-timestamp` (Unix seconds of this attempt) and `webhook-signature`.
   - The signature is `v1,<base64 HMAC-SHA256(key, "<webhook-id>.<webhook-timestamp>.<raw body>")>`, where `key` is the base64-decoded secret after its `whsec_` prefix.
   - During a rotation the header carries two signatures separated by a space.
   - Receivers reject a timestamp more than 5 minutes from now, compare in constant time, and deduplicate on `webhook-id`.
   - `X-Eeasy-Event-Type` and `X-Eeasy-Delivery-Id` stay as unsigned copies for logging, never trusted without the signature.
2. **Secrets.** Each subscription has its own `whsec_<base64 of 32 random bytes>` secret, generated by us, shown once in the create or rotate response and stored encrypted. Rotation issues a new secret and signs with both for 24 hours.
3. **Asymmetric signatures (`v1a`, Ed25519)** are not offered now: no official library implements them yet. Adding them later is an addition to this ADR, not a format change.
4. **Delivery (unchanged).**
   - At least once, from the outbox (ADR-0024). One in-flight delivery per subscription and aggregate, in `sequence` order. A 10-second timeout.
   - Exponential backoff for up to 24 hours, then `dead`; dead deliveries are listed in the merchant web app and can be redelivered.
   - **New, from the specification:** a `410 Gone` response disables the subscription at once and notifies the account owner. A `Retry-After` header on a `429` or `503` is honoured, capped at the next step of the schedule and within the 24-hour window.
5. **Subscription verification (unchanged).** A new or re-pointed subscription stays `pending_verification` until the integrator returns the one-time token we sent, in a signed `webhook.verification` request, to the URL. The token is stored only as a hash. The specification's synchronous challenge extension is not used, because it fails for receivers behind queues.
6. **URL safety (unchanged).**
   - URLs must be `https` on port 443. The API checks only syntax and address class at creation; reachability and the verification request run through the outbox.
   - Each delivery resolves the host once and refuses private, loopback, link-local, `0.0.0.0/8`, `100.64.0.0/10`, `198.18.0.0/15`, multicast and IPv4-mapped IPv6 addresses. It connects to the checked address and follows no redirect.
   - The delivery log exposes the status code and a fixed error class, never the response body.
   - Subscription creation and URL changes are limited to 5 per hour per account.
7. **Sender implementation.** The worker signs with the `standardwebhooks` npm library, pinned exactly, or with an equivalent of the specification's reference algorithm. A conformance test checks our signatures against the fixed examples in the official libraries' test suites (for example `libraries/php/tests/WebhookTest.php` and `libraries/python/tests/test_webhooks.py`), and verifies one of our deliveries with the official PHP and Python verifiers.

## Consequences

A merchant verifies a delivery with one call to the official library for their language, or with any Svix-compatible tooling, instead of copying our snippet. The signed id binds the signature to one message as well as one body and one time. The format is fixed by an external specification, so our documentation links to it and adds only our event catalogue, ordering and retry rules. The relay needs a `410` path and `Retry-After` handling. `docs/contracts/webhooks.md` §2 and §3 and the `public.yaml` webhook header parameters change in the same PR as this ADR. INT-10 builds it.

## Alternatives considered

- **Keep ADR-0030's own format.** Equally secure, but every merchant hand-writes the verification, and our headers match no library. It lost because the specification costs us nothing before INT-10 and saves every integrator work.
- **Stripe's scheme.** Widely copied, but specific to Stripe with no neutral libraries.
- **Ed25519 now.** Better when the producer and consumer are separate parties, but no official library verifies `v1a` today.
- **Mutual TLS.** Strong, but too heavy for most Saudi merchant stacks (as in ADR-0030).
